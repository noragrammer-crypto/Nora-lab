## AIコーディングエージェントを使っていると、最初はかなり快適

「この機能を作って」

と頼めばコードを書いてくれる。

しかし、プロジェクトが大きくなってくると、別の問題が出てきます。

- この実装、本当に正しいのか
- 既存機能を壊していないか
- ドキュメントは追随しているか
- AIが「できました」と言っているけれど、本当に終わっているのか
- 毎回、人間がコードを全部読んで判断する必要があるのか

AIがコードを書く能力そのものより、**AIにどう仕事をさせ、どう合格判定するか**の方が重要になってきます。

そこで個人開発用に作ってきたのが **SoloXP** です。

今回、実際に使っているスキル定義・ワークフロー・ドキュメント一式をOSSとして公開しました。

GitHub（日本語版）:
https://github.com/noragrammer-crypto/Nora-lab/tree/main/tools/SoloXP/Ja

英語版もあります:
https://github.com/noragrammer-crypto/Nora-lab/tree/main/tools/SoloXP/en

## SoloXPとは

SoloXPは、**AIコーディングエージェント時代に、個人でも一定の開発プロセスに従ってソフトウェアを作るための仕組み**です。

最近の言葉を使えば、ハーネスエンジニアリングの一例になると思います。

ベースにある考え方はXP（Extreme Programming）ですが、AIエージェントとの協働を前提にかなり作り替えています。

基本単位はGitHub Issueです。

```
Issue
  ↓
Tester
  ↓
Implementer
  ↓
Auditor
  ↓
Documenter
  ↓
Auditor
  ↓
Pull Request
```

人間が毎回、

「次はテストを書いて」
「では実装して」
「ちゃんと動くか確認して」
「ドキュメントも更新して」

と指示するのではなく、それぞれを役割として分離しています。

---

## 1タスク1PRの「デルタ」を積み上げる

SoloXPでは、大きな完成形を一度にAIへ渡すより、**小さな変更をIssueとして切り出し、その差分を積み上げていく**ことを重視しています。

基本は、

```
1 Issue = 1 Task = 1 PR
```

です。

例えば、「ユーザー管理機能を作る」という大きな指示をそのまま投げるのではなく、

- #101 Userモデルを追加
- #102 UserRepositoryを追加
- #103 ユーザー登録APIを追加
- #104 登録フォームを追加

のように分解します。

各Issueは、それ単独で

- 実装できる
- テストできる
- レビューできる
- PRとしてマージできる

程度の大きさにします。

巨大な仕様書をAIに読ませ続けるのではなく、GitHubに過去のIssueとPRを残しながら、システムを少しずつ変化させていく考え方です。

---

## TDDを合格判定として使う

SoloXPはTDDをかなり強く使います。

これは「TDDこそ正義」という思想だけが理由ではありません。AIエージェントを使う場合、**人間の代わりに何が合否を判定するのか**という問題があるからです。

AI自身に、

> 良い感じにできた？

と聞けば、多くの場合、

> できました。

と返ってきます。これでは品質ゲートになりません。

そこで先にTesterがテストを書きます。

```
RED
 ↓
Implementerが実装
 ↓
GREEN
```

このGREENを、AIに対する明示的な終了条件として利用します。

つまりSoloXPにおけるテストは、単なる品質保証だけではなく、**AIエージェントに仕事の終了条件を与える仕組み**でもあります。

---

## 「実装するAI」と「合格判定するAI」を分ける

もう一つ重要なのが役割分離です。

例えばImplementer自身に、

> 実装してください。終わったら正しく実装できたか確認してください。

と頼むこともできます。ただ、自分で書いたものを自分で採点すると、どうしても判断が甘くなります。

SoloXPでは役割を分けています。

**Tester**
要求をテストへ変換します。

**Implementer**
テストをGREENにする実装を担当します。

**Auditor**
テスト結果や変更内容を確認し、合格・差し戻しを判断します。

**Documenter**
仕様書や関連ドキュメントを更新します。

**Director**
これらの進行を管理します。

人間の開発組織で行っていた分業を、そのままAIエージェント用のワークフローとして再構成したようなものです。

---

## Human-in-the-Loopでも完全自律でもない

SoloXPの標準運用では、人間はあまり細かく介入しません。基本的には、

```
人間 → Issueを作る

AI  → テスト → 実装 → 監査 → ドキュメント → PR作成

人間 → PRを確認してマージ
```

という構造です。

逐一人間が承認するHuman-in-the-Loopほど重くない。一方で、AIが勝手に全部マージする完全自律でもない。その中間なので、自分では **Human-on-the-Loop** と呼んでいます。

人間は作業そのものから少し離れ、**何を作るかと、最終的に採用するか**を見る立場になります。

---

## 実際の使い方

現在の公開版では、Claude Codeを使う場合、最短では次の流れです。

最初にSoloXPのスキルを `.claude/skills/` などへ登録し、`CLAUDE.md.template` を自分のリポジトリの `CLAUDE.md` へコピーします。

あとはIssueを作り、

```
/xp_Director <Issue番号>
```

を実行します。

そのIssueが `[Task]` で、かつ外部から観測可能な振る舞いの変化を伴わない（ドキュメント修正や内部リファクタなど）ものであれば、1回のランで以下がそのまま流れます。

```
xp_Tester
 ↓
xp_Implementer
 ↓
xp_Auditor
 ↓
xp_Documenter
 ↓
xp_Auditor
 ↓
PR
```

一方、`[Story]` や `[Bug]`、タグなしの大きめのIssue、あるいはAPI・UIの変更など観測可能な振る舞いを伴う `[Task]` を渡した場合は、いきなりこの流れには入りません。まず Architect が判断・分解を行い（必要ならE2E/仕様書サブタスクも発行し）、`[Story]`/`[Bug]` の場合はブランチを作成してそこで一旦停止します。以降は分解されたサブタスクを1つずつ、`/xp_Director <サブタスク番号>` で個別に実行していく形になります（**1回のランにつき1タスク1PRが原則**）。

すべてのサブタスクPRがマージされたら、それで終わりではありません。もう一度 `/xp_Director <親Issue番号>` を実行し、Story全体としてのテスト（AllGREEN判定）とレビューを経て、親ブランチからmainへの最終PRを発行します。

実行中の進捗はGitHub Issueにも残ります。例えば、あるサブタスク（`[Task]`）を1回のランで処理すると、

```
[Tester完了] tests/unit/dateFormat.test.js を追加
[Implementer完了] lib/dateFormat.js を実装
[Auditor GREEN] 全テストpass
[Documenter完了] docs/spec/dateFormat.md を更新
[Auditor doc OK]
[PR発行済み #102]
```

のような形です。Issueが作業指示書であると同時に、作業記録にもなります。

---

## バイブコーディングより、かなり重い

ここは重要なので書いておきます。SoloXPは、**最速で何かを作りたい人向けではありません**。

テストを書き、実装し、監査し、ドキュメントまで更新するので、当然ながら重いです。小さな試作品なら、「これ作って」とAIに一発で作らせる方が速いでしょう。

SoloXPが欲しくなるのは、その次の段階です。機能が増え、「この変更、本当に既存部分を壊してない？」という判断が人間側の負担になってきた時です。

AIが賢くなるほどコード生成量は増えます。すると人間側のボトルネックは、**コードを書くことから、生成された変更を評価することへ**移ります。SoloXPは、その評価工程まで含めてAI側へ移すことを狙っています。

---

## 実はスマホ開発との相性が良かった

これは当初あまり狙っていなかった副作用です。自分はClaude Code WebをAndroidから使うことがかなりあります。

スマホでコードを細かく編集するのはつらいですが、

```
Issueを作る → AIに渡す → PRを見る
```

だけなら、それほど苦になりません。実装途中のAIと延々チャットする必要もありません。

作業単位をIssueとしてGitHubに置いてしまえば、途中でスマホを閉じても状態が消えません。まとまったPC作業時間を取りにくい環境では、案外この構造が便利でした。

---

## Claude Code専用なのか

現状、最も実運用しているのはClaude Code、特にClaude Code Webです。

ただし設計としては、Director / Tester / Implementer / Auditor / Documenter という役割とGitHub上の状態遷移が本体なので、Claude Codeだけに限定するつもりはありません。Codexなど別のAIコーディングエージェントでも動かせる形を目指しています。

ただし公開時点では、Claude Code以外について十分な動作保証ができる状態ではありません。Claude Codeについても含め、基本的には **No Warranty** です。

## 公開した理由

SoloXPは最初からOSSとして設計したものではありません。自分の個人開発を楽にするために作った、かなり個人的な仕組みでした。

しかし実際にIssueとPRを大量に流していると、

- AIの能力より終了条件の設計が重要
- 巨大なプロンプトより小さなIssueの方が扱いやすい
- 実装AIと評価AIは分けた方が安定する
- AIにも普通の開発プロセスを守らせた方がよい
- GitHub自体がエージェント間の共有メモリとして機能する

といった知見が溜まってきました。

これは自分だけの環境依存ノウハウというより、**AIコーディングエージェントを継続運用すると、多くの人がそのうちぶつかる問題なのではないか**と思っています。

そこで、スキルだけではなく、

- README
- インストール手順
- セットアップ
- チュートリアル
- ブランチ戦略
- ワークフロー仕様
- 過去の設計資料

まで含めて公開しました。現在の実装だけでなく、なぜこうなったのかもある程度追えるようにしています。

## こんな人には面白いかもしれません

特に、

- Claude CodeやCodexを日常的に使っている
- AI生成コードのレビュー量が増えてきた
- バイブコーディングから少し大きな開発へ進みたい
- TDDとAIエージェントの組み合わせに興味がある
- GitHub Issue / PRをAIの作業基盤として使いたい
- マルチエージェントやハーネスエンジニアリングに興味がある

という人には、何か参考になる部分があると思います。

完成された万能フレームワークというより、**AIコーディングエージェントを「作業者」として運用するにはどういう仕組みが必要なのか**を実際の個人開発で試し続けている実装例、と捉えてもらうのが一番近いです。
