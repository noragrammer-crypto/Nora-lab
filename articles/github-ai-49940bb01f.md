## 「そんな雑な一行で、AIはちゃんと動くのか？」

前回の記事では、イシューが立った後にAIがどうやってタスクに分解し、PRとして仕上げるかという「コード化フェーズ」を紹介した。

ここで一つ、当然の疑問が残る。

その最初のイシュー自体は、誰がどうやって立てているのか。

答えは拍子抜けするほど雑だ。私は思いついたことを、推敲もせず一行だけ書く。たとえば「E2Eの既存REDの所有権なんとかする」とか、その程度のメモに近い一文である。要件も背景も書かない。

普通に考えれば、こんな一行だけ渡されてもAIは何をすればいいか分からないはずだ。ところが実際には、これで動く。なぜか。

## 一行イシューが「復元」されるまで

種明かしをすると、AIはその一行だけを読んで仕事をしているわけではない。

リポジトリには、これまでのIssue・PR・実装コード・テスト・過去の判断履歴、そしてCLAUDE.mdやスキル定義が積み上がっている。AIはイシューを受け取ると、この蓄積されたコンテキストを横断的に探索する。

先ほどの「E2Eの既存REDの所有権なんとかする」という一行を例にとる。AI（Architect役）はこれを渡された時点で、

-

関連する過去のIssue・PRを検索し、「REDの所有権」がどの機能・どのテストを指しているかを特定する

-

現在の実装とテストコードを読み、何が「既存の」状態なのかを確認する

-

CLAUDE.mdやWORKFLOW.mdに定義された役割分担（Tester→Implementer→Auditor→Documenter）に沿って、次にやるべきタスクを組み立てる

という形で、一行の意図と蓄積されたコンテキストを掛け合わせ、実行可能な粒度のイシューへと組み立て直す。

```
ワンラインの意図 + 蓄積されたコンテキスト → かなり具体的なイシュー

```

つまりGitHubは、私にとって単なるタスク管理・ソースコード管理の場所ではない。AIの外部記憶装置として機能している。Issue やPRは進捗の記録である以上に、次にAIが仕事をするときに「意図を補完するための素材」なのである。

## それでも人間の仕事は残っている

とはいえ、すべての一行イシューがそのまま起票されるわけではない。実際の流れは次のようになっている。

-

**思いついたことを一行イシューに書く**（人間） 推敲しない。抽象的で雑なままでいい。目的はただ一つ、思いついた瞬間を揮発させずに残すこと。

-

**AIと相談して実行可能な粒度に詰める**（人間＋AI） 一行のままでは、まだタスクに分解できるほど具体的ではないことが多い。「これは何をもって完了とするか」「どこまでをこのイシューの範囲にするか」を、AIとの対話で詰めていく。

-

**AIがイシューとして起票する**（AI） ここで固まった内容を、AIがイシュー本文として整形する。このとき大事なのは、新しく別のイシューを作らないこと。最初に立てた一行イシューを、本文編集で育てていく。新規に切り出してしまうと、元の雑なイシューが放置されたまま残ってしまい、後の処理で誤って拾われる事故につながるからだ。

ここでようやく、前回記事で説明した4段階フロー（タスク分解→実装→受け入れテスト→PR発行）の入口に乗る。

## PRができて終わり、ではない

コード化フェーズを経てPRが上がってきたら、人間が差分を読んで確認する。マージとイシュークローズは、最終的には必ず人間の判断に残している。AIにどこまで事前承認の範囲を与えていても、ここだけは譲らない。

そして、マージして終わりにしない。実際にその機能を使ってみて、狙い通り動いているか、想定外の挙動はないか、次に欲しい改善は何かを確認する。

この評価のステップを飛ばすと何が起きるか。PRの生産速度自体は上がる。だが、それが本当に前進なのかを確かめる工程がないまま、的外れな実装が積み上がっていくリスクがある。「量産できている」ことと「前進している」ことは別物だ。

そして評価から得た気づきは、必ずまた一行イシューとして書き留める。感想のまま流さない。ここで外部化を怠ると、外側のループはそこで途切れてしまう。

## ループは回るほど強くなる

ここまでを図にすると、こうなる。

```
思いつき
   │ 一行イシュー
   ▼
AIとの相談で具体化
   │ 起票
   ▼
4段階フローでコード化（分解→実装→受け入れテスト→PR）
   │ PR
   ▼
人間による確認・マージ
   │ 使ってみる
   ▼
評価
   │ 気づき
   └──▶ 新しい一行イシューへ

```

この6ステップのループには、複利のような性質がある。

Issueを書く → PRができる → 判断の履歴が残る → 次のIssueを書く → AIが過去を参照して意図を補完する → またIssue/PRが増える。

このループを1周するたびに、GitHubに蓄積される外部記憶は厚みを増していく。厚みが増すほど、次に一行だけ書いたときにAIが復元できる精度が上がる。つまり「一行イシューだけで足りる」という状態は最初から成立していたのではなく、このループを回し続けた結果として育ってきたものだ。

## 仕様書を捨てたわけではない

こう考えると、私がやっていることは「仕様書を書かない開発」ではないと分かる。むしろ逆で、

**大きな仕様書を先に一箇所に書き切るのではなく、小さなIssue/PRを回し、その履歴自体を次の仕様理解のコンテキストにしている**

だけだ。仕様を書く行為そのものを放棄したわけではなく、仕様を一つの巨大な文書に固定するのではなく、コードとIssue/PRの履歴の中に少しずつ育てている、というのが実態に近い。

一行のメモから始めて、AIとの対話で具体化し、小さく実装し、使ってみて評価し、また次の一行に戻る。この地味な往復こそが、ソロ開発でも仕様が痩せていかない理由だと思っている。
