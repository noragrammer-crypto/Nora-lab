## なぜSoloXPか

Claude Codeを使い始めて最初に試したのはバイブコーディングだった。簡単なものはすぐ動く。でもちょっと複雑になった途端、行き当たりばったりになる。何をやっているのか見えなくなる。その気持ち悪さに耐えられなくて断念した。

ウォーターフォールは論外。ならば、昔から自分の肌に合っていたXPのワークフローを土台にしよう、という判断に至った。チームでやるわけではないので、「人間とAIの協働がうまく回る」ように調整しながらワークフローを育てていく形に。それがSoloXPと名付けた理由だ。

内容的にはコンテキストエンジニアリングを軸にしつつ、気づけばハーネスエンジニアリングの領域にも踏み込んでいた。

---

## 環境と形態

**スマホでほぼカバーできる**

メインはAndroidアプリ経由のClaude Code Web。E2EテストやClaude Code Webでやりきれない処理はGitHub Codespacesで補完。ヘッドありブラウザが必須な部分だけ、たまにオンボロPCが出番を持つ。

マルチエージェント構成も当初は検討したが、Claude Code Webがメインである以上シングルスレッドが基本。並列処理が必要なら、Claude Code Webのスレッドを複数同時起動することで対応できる。

## SoloXPの6つの特徴

### 1. イシュードリブン × ノーチャット × 1タスク1PR1clear

チャットしない。これが肝だ。新規スレッドをどんどん立てて処理していく形なので、「前の指示を忘れる」という問題はそもそも設計で封じる。コンテキストをきちんと引き継がせる仕組みを最重視した。

### 2. アーキテクトによるイシュー分解とタスク化

タスク粒度が安定することで、1タスクあたり早いもので5分、長くても30分以内に収まるようになった。これが実装の安心感につながっている。

### 3. TDDの徹底

XP準拠なので当然TDDを実行する。E2EテストはVercel自動デプロイに対して行うのがメイン。Function Test・Unit Testも含め、テストが「壁」として機能することでエージェントの探索空間を制約できる。

### 4. Tester / Implementer / Auditor による三権分立ループ

この構造を入れてから、実装が安定して前に進むようになった。役割の分離がエージェントの暴走を抑止する。

### 5. 過剰なほどのドキュメント化

イシューとして降ってくる細かい機能仕様変更・差分（＝デルタ）を、機能仕様として積分して管理するのが目的。GitHubイシューとPRを組み合わせれば、過去の判断経緯はいつでも遡れる。SSOTをプロセスとして設計している。

### 6. コンテキストの永続化

CLAUDE.md・SKILL.mdによるセッション横断的な知識の保持。これがノーチャットを成立させるインフラになっている。

## まとめ

日曜大工から始まったはずが、スケールが見えてきた。

ソロ開発でもプロセスをきちんと設計すれば、エージェントは「行き当たりばったりの助手」ではなく「ロールを持った精霊」として機能する。それがSoloXPの正体だと思っている。
