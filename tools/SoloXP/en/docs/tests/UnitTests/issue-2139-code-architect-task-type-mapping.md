# Unit Test: issue-2139 code-architect-task-type-mapping

## Background

`#2100` (functional specification update task) is for updating `SoloXP/docs/spec/xp_architect.md`.
It was explicitly requested to "specify the output conversion rules (depends_on / task_type mapping)", but
The actually added `code-architect 出力 → xp 実行計画へのマッピング` table is a link to `depends_on`.
It only defined conversion rules and did not mention `task_type` at all.

`xp_Director` distributes processing depending on the presence/absence and value of the `task_type:` field in subissues.
(`e2e_test_creation` / `spec_update` / `bug_reproduction_test` / normal implementation tasks), this omission is
"How should `task_type` be assigned to subissues generated by code-architect" is documented in the specifications
(Codex automatic review pointed out #2139).

When I checked the actual design, I found that the sub-issues generated from code-architect's Build Sequence are
Always published as a "normal implementation task" without the `task_type` field (normal format from step 5),
`task_type: e2e_test_creation` / `spec_update` involves Story issues and observable behavior changes
If it is a Task issue, regardless of the output content of code-architect, it will be added as a “required additional task” in step 5.
It was designed to be published separately in a fixed format. This design itself worked correctly, but
It could not be read from the mapping table and had to be clearly stated.

## Test case

For each copy of `dotfiles/` and `SoloXP/` (`describe.each`):

1. There is a line explaining how to handle `task_type` in the mapping table.
2. It is clearly stated that task_type is not derived directly from code-architect output.
3. It is clearly stated that e2e_test_creation/spec_update is fixedly issued separately regardless of the output of code-architect.
