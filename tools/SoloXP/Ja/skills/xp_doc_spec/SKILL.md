# XP Doc Spec Skill

## コマンド

### `xp_doc_spec <epic_name> <issue_number>`

機能仕様書を生成・更新する。
**ストーリーカード = 差分（delta）、spec = 積分（integral）** の思想で運用する。

---

## 処理フロー

### 1. 対象ディレクトリを決定する

以下の優先順位でspecディレクトリを決定する：

| 優先度 | specディレクトリ |
|--------|------------------|
| 1（優先）| `api/<EpicName>/docs/spec/` が存在する場合 |
| 2（フォールバック）| `<EpicName>/docs/spec/`（HolyAutomater は `api/` 配下を Vercel Function エントリポイント専用とするモノレポ構成のため、大半のエピックはこちら） |

以降の手順の「specディレクトリ」はここで決定したディレクトリを指す。

### 2. 現状の機能領域マップを把握

specディレクトリの `README.md` を読む。

### 3. Issue本文＋コメントを全読み

- GitHub Issue の内容・コメント全履歴を取得する（`gh` または MCP）
- 仕様変更はコメントに埋まっていることが多いため全件確認する

### 4. 既存specとの差分を特定

- specディレクトリ以下の全MDを読む
- 今回のIssueで追加・変更される仕様を特定する

### 5. 差分を積分

- 既存領域なら該当MDを更新する
- 新規領域なら新ファイルを作成する
- 1ファイルが200〜500行を超えそうなら適切に分割する

### 6. 索引を更新

specディレクトリの `README.md` の索引を更新する。

### 7. 関連イシュー表の状態を同期する

`README.md` の「関連イシュー」表に記載された各イシュー番号について、実際の Issue 状態（open/closed）を取得し、表の状態列を最新化する。

- `gh issue view <番号> --json state` または MCP `mcp__github__issue_read`（method: `get`）で現状態を取得する
- 表の状態列が実態とズレている行（クローズ済みなのに `open` のまま等）を修正する
- README が陳腐化したまま放置されることを防ぐための必須ステップ

---

## アウトプット

- specディレクトリの `README.md`（更新）
- specディレクトリの `<領域>.md`（新規 or 更新）

---

## 注意事項

- spec → stories の逆方向（specからストーリーを生成する等）はしない
- spec は「今の実装の正」を記録する。将来対応は書かない
