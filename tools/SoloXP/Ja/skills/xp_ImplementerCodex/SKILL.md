# XP Implementer Codex Skill

## コマンド

### `xp_ImplementerCodex <#issue番号>`

タスクイシューを読み込み、**テスト作成（Tester相当）と実装（Implementer相当）の両方を Codex CLI（`codex exec`）に委任して** 行う。
既存テストが無い場合はCodexがテストも書く（TDD）。既存テストがある場合（バグ修正フォロー等）は実装のみ委任する。
完了報告フォーマットは `xp_Implementer` を拡張したもの。単体テスト・機能テストのグリーンを目標とする。

> **呼び出し元**: `xp_Director <issue番号> implementer=codex` から呼ばれる。
> `xp_Tester` + `xp_Implementer`（または`xp_ImplementerCodex`旧版）の代替であり、通常実装タスク
> （`e2e_test_creation` / `spec_update` / `bug_reproduction_test` を除く）のみが対象。
> `implementer=codex`指定時、Directorはこのスキルを呼ぶ前に`xp_Tester`を呼ばない
> （本スキルがTesterの役割も内包するため）。

**Claudeが握る境界**: Architect（設計・分解）・E2Eテスト作成（受け入れ条件の定義）・Story-level受け入れ判定は
引き続きClaudeが行う。本スキルはあくまでサブタスクレベルのテスト作成・実装のみを委任する。

---

## 責務

- Codex CLI にテスト作成（必要な場合）と実装を委任する
- **Codexの自己申告は信用しない。** 完了後に自分でテストを実行し、結果を記録する
- 結果にかかわらず xp_Director に返す（Director が Auditor を呼ぶ）

**テストの正しさの判断は Auditor の責務。本スキルは判断しない。**
Codexがテストと実装の両方を書くため、**Auditorによる独立したテスト再実行が唯一の第三者チェックになる**
（xp_Auditorはこれまで通り`xp_RunTestSuites`/`xp_RunE2ETests`経由で必ず自分でテストを再実行する。この安全網は無改修）。

## 動作手順

### 0. 着手前チェック

`xp_Implementer` と同一。

#### ブランチ確認
- ClaudeCode Web の場合：タスク起動時に自動生成されたブランチを確認する
- ローカル / Codespaces の場合：作業用ブランチを作成する
  ```bash
  git checkout -b feature/issue-{番号}-{概要}
  ```
- **main ブランチのまま作業を開始しない**
- **リポジトリルートの `Codex.md` / 各プロジェクトディレクトリの `Codex.md` に書かれた `feat-<Issue番号>` ブランチ命名・`git worktree` 分離の規約はここでは適用しない。** それらはCodexを単独運用する場合の規約であり、Solo XPのサブタスクフローでは既存のSolo XPブランチ運用（本セクション）を優先する。

#### 依存イシューの確認
- イシューの `depends_on` フィールドを確認する
- 依存イシューがある場合、**依存先サブイシューのコメントに `[Auditor GREEN]` があるかを確認する**
- `[Auditor GREEN]` がない場合は着手しない。イシューにコメントして終了する：
  ```
  ⚠️ 着手ブロック: Issue #XX の [Auditor GREEN] がまだ記録されていません。
  完了後に xp_Director から再度呼ばれます。
  ```

#### Codex CLI 疎通確認
- `codex --version` でCLIが利用可能か確認する
- `~/.codex/auth.json` が存在しない場合（`CODEX_AUTH_JSON_B64` 未設定等）は着手せず、xp_Director に報告して終了する：
  ```
  ⚠️ Codex CLI が利用できません（認証未設定）。xp_Implementer（Claude版）へのフォールバックを検討してください。
  ```

### 1. マーカーを記録する

イシューにコメントを記録する（テスト新規作成が必要かどうかは手順3判定後に判明するため、判定結果も併記する）:
```
[Tester実行中][Implementer実行中]
実装エージェント: Codex CLI (codex exec)
```

### 2. タスクイシューを読み込む

`xp_Implementer` と同一。以下を把握する：
- 実装すべき機能・処理
- 見積もり（pt・note）
- 親ストーリーイシュー
- 既存のテスト（UnitTest / FunctionalTest）
- エピック名（`epic/<EpicName>` ラベルから取得）

### 3. 既存テストの有無を判定する

- `<EpicName>/__tests__/` に、このタスクの受け入れ基準となるテストが既に存在するか確認する
  （バグ修正フォロー等、直前のサブタスクで`xp_Tester`がテストを作成済みのケースを含む）
- **既存テストがある場合（実装のみモード）**: そのテストの期待動作を把握する。手順4のプロンプトは実装のみを依頼し、
  「テストファイルは変更・削除しないこと」の制約を維持する
- **既存テストがない場合（テスト作成込みモード）**: イシュー本文の受け入れ条件からテストで検証すべき命題を把握する。
  手順4のプロンプトはテスト作成（TDD）＋実装の両方を依頼し、この場合に限り
  「テストファイルは変更・削除しないこと」の制約を外す（Codexがテストの著者になるため）

### 4. Codex 実行プロンプトの組み立て

以下を1つのプロンプトにまとめる：

1. イシュー本文（実装すべき内容・見積もり）
2. **実装のみモード**: 既存テスト（手順3で読んだファイルの該当箇所）の期待動作を伝え、それをGREENにする実装を依頼する
   **テスト作成込みモード**: イシュー本文の受け入れ条件を伝え、「まず`<EpicName>/__tests__/unit/`・`functional/`に
   テストケースを作成し（命題を明確にすること。テストを歪めてGREENにしない）、その後そのテストをGREENにする実装を行うこと」を依頼する
3. 対象エピックディレクトリの `Codex.md` が存在する場合はその内容（ディレクトリ固有の作業ルール・テストコマンド）
4. 明示的な制約（**必ず含める**）：
   ```
   - 新規ブランチ・git worktree を作成しないこと。現在チェックアウト済みのブランチで直接ファイルを編集すること。
   - 既存コードのスタイル・設計に合わせ、過度な抽象化・将来対応は行わないこと。
   - セキュリティ上の問題（インジェクション・XSS等）を発生させないこと。
   - このタスクの範囲外のファイルは変更しないこと。
   ```
   実装のみモードの場合は追加で：
   ```
   - テストファイル（__tests__/ 配下）は変更・削除しないこと。
   ```

### 5. Codex CLI 実行

```bash
codex exec \
  --sandbox workspace-write \
  --cd <対象エピックディレクトリの絶対パス> \
  --json \
  -o /tmp/codex-last-<issue番号>.txt \
  "<手順4で組み立てたプロンプト>"
```

- `--sandbox workspace-write` を用いる（承認プロンプトは出ない = full-auto相当。`--dangerously-bypass-approvals-and-sandbox` は使わない）
- プロキシ環境変数はセッション側で設定済みのため追加設定は不要
- 実行ログ（`--json` の出力）は異常終了時の調査用に残す

### 6. テスト実行（Codexの自己申告は使わない）

`xp_Implementer` 手順5と同一。Codexの完了メッセージに記載された結果を鵜呑みにせず、必ず自分で実行する：

```bash
# 単体テスト
npm test -- --testPathPattern="unit"

# 機能テスト
npm test -- --testPathPattern="functional"
```

結果を記録する。GREEN でも RED でも次のステップへ進む。
**テストに疑念があっても自己判断で止まらない。Auditor に引き継ぐ。**

### 7. 変更内容の把握

```bash
git diff --name-status
```

の出力から変更ファイル一覧を取得する（Codexの自己申告ではなく実際のdiffを使う）。

### 8. xp_Director に結果を報告して終了

`xp_Implementer` の完了報告フォーマットを拡張。テスト作成込みモードの場合は命題一覧も含める：

```
## 実装完了

実装エージェント: Codex CLI (codex exec)
モード: 実装のみ / テスト作成込み

<テスト作成込みモードの場合のみ>
## テスト命題（Unit/Functional、Codexが新規作成）

- [x] <命題1>
- [x] <命題2>

変更ファイル:
- `<path>`: <変更内容>（テスト作成込みモードでは、変更ファイルにテストファイルも含まれる）

テスト結果:
- 単体テスト: PASS n件 / FAIL n件
- 機能テスト: PASS n件 / FAIL n件

<テストに疑念がある場合>
⚠️ 以下のテストについて Auditor に確認を依頼します:
- <テスト名>: <懸念内容>
```

## 注意事項

- 実装のみモードでは、テストのグリーンを目的にテストを修正・削除してはならない（Codexへのプロンプトにも明記する）
- テスト作成込みモードでは、Codexがテストと実装の両方の著者になる。**テストを歪めて自明にGREENにしていないか
  （命題が空虚でないか）は、Claude自身も変更ファイルとテスト内容をざっと確認する**（Auditorほど深くは検証しないが、
  「テストが何も検証していない」ような明らかなケースは差し戻す）
- テストに疑念があっても自己判断で止まらず、必ず xp_Director 経由で Auditor に引き継ぐ
- E2E テストは本スキルでは対象外（受け入れ条件の定義はClaudeの`xp_E2Etest`が担い、Story完了時にClaudeが確認する）
- Codex CLI はユーザー個人のChatGPT OAuth認証（`CODEX_AUTH_JSON_B64`）で動作する。Codex側の利用枠を消費する点に留意する
- `xp_Auditor` は本スキルの完了報告を信用せず独立にテストを再実行する。テストも実装もCodexが書くテスト作成込み
  モードでは、この独立再実行が唯一の第三者チェックになるため、Auditor側の手順は一切省略しない
