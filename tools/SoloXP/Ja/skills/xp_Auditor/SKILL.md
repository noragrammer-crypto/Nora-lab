# XP Auditor Skill

## コマンド

### `xp_Auditor test <epic> <issue>`

テストを実行し、結果を分析してイシューにコメントする。
xp_Director に結果を返す。**ワークフロー制御は xp_Director の責務。**

### `xp_Auditor doc <epic> <issue>`

ドキュメントをチェックし、結果を xp_Director に返す。PR 発行は xp_Director の責務。

---

## 責務

- テストの実行・結果報告（ワークフロー制御はしない・Director に返すだけ）
- エラーのスコープ判断（同一タスク内 or 別タスクのバグ）
- 別タスクスコープのバグ発見時：バグイシューを新規発行
- ドキュメントのチェック・報告
- ドキュメントチェック結果の報告（PR発行は xp_Director の責務）

**ファイルへの書き込み権限はない（PR発行・Issueコメント・Issueの新規発行を除く）。**

---

## ⚠️ 重要: テスト実行ルール

**直接テストコマンド（npx jest, pytest 等）を実行してはならない。**

テスト実行は必ず以下のスキル経由で行うこと：

- Unit + Functional テスト → `xp_RunTestSuites` SKILL.md を読み込み、その手順に従う
- E2E テスト → `xp_RunE2ETests` SKILL.md を読み込み、その手順に従う

---

## 処理フロー（test モード）

### 1. イシューを読み込む

- GitHub Issue の内容・コメント履歴を取得する
- 対象のテストファイル・実装ファイルを特定する
- **現在処理中のタスクスコープ（どのタスクイシューか）を把握する**
- 過去の Auditor コメントがあれば経緯を把握する
- イシュー種別を確認する（ストーリーイシューか、タスクイシューか）

### 2. xp_RunTestSuites を実行する

`xp_RunTestSuites` SKILL.md を読み込み、その手順に従って Unit + Functional テストを実行する。

結果（標準出力・エラー出力）を全文記録する。

### 3. E2E テストの判断・Story-level Auditor フェーズ

タスクイシュー単体の場合は E2E をスキップする（記録不要）。

ストーリーイシューを受け取った場合（タイトルに `[Story]` タグ、または xp_Director から AllGREEN 後に呼ばれた場合）は以下の **Story-level Auditor フェーズ** を実行する。

**Story-level Auditor フェーズ（xp_Auditor test \<epic\> \<story\>）**

1. 親ブランチ `feature/issue-{story}` に対して E2E テストを実行する（`xp_RunE2ETests` SKILL.md を読み込み手順に従う）

2. GREEN の場合：ストーリーイシューに `[Auditor GREEN]` を記録する

   **GREEN を xp_Director に返す。xp_Reviewer 呼び出し・PR発行・ストーリークローズは xp_Director の責務。**

3. RED の場合：失敗した E2E テストの内容でバグイシューを起票する
   - 起票前に同内容のオープンな `bug` イシューが既に存在しないか確認する（`search_issues` の `label:bug` + キーワード）
   - **既存イシューが見つかった場合**: 新規発行せず、既存イシューへ重複検知コメントを追加する
     （`workflow/docs/spec/issue-triage.md` 3節のプロトコル、`<!-- hot-issue-dup -->` マーカー必須）。
     既存イシューの親を確認する（`mcp__github__issue_read` method: `get_parent`）。GitHub の
     サブイシューは親を1つしか持てず、`mcp__github__sub_issue_write` の `add` で親を
     付け替えるには `replace_parent: true` が必要——安易に付け替えると元の親ストーリー側の
     `xp_Director` 追跡が壊れるため、次のように扱いを分ける：
     - **親が未設定の場合**: このストーリーのサブイシューとして追加する。`xp_Director` は
       サブイシュー経由で未完了作業を検出するため、紐付けがないとバグが放置されたまま
       同じ RED・重複検知コメントのループになってしまう
     - **既に別の親（他のストーリー等）に紐付いている場合**: 付け替えない。別ストーリーの
       追跡を壊さないことを優先し、重複検知コメントとストーリーへの参照記録のみに留める
     ストーリーイシューには既存イシュー番号を参照として記録する
   - **見つからない場合**: 新規バグイシューを起票する
     - バグイシューの本文に `## 親ブランチ: feature/issue-{story}` を含める
     - 起票したバグイシューをストーリーのサブイシューとして追加する
     - ストーリーイシューに失敗内容とバグイシュー番号をコメントする
   - ストーリーは継続（クローズしない）

4. E2E 実行不可の場合：`[E2E スキップ]` コメントを記録し、ユーザーに判断を委ねる（自動クローズしない）

### 4. 結果を分析する

各 FAIL テストについて以下を判断する：

**エラーのスコープ判断（最重要）**
- このエラーは現在処理中のタスクイシューのスコープ内か？
- 別のタスク・別の機能領域に起因するエラーか？

**テスト設計の問題**
- モックの設定ミス（`jest.resetModules()` 後に別インスタンスを掴んでいる等）
- テストの期待値が仕様と合っていない
- テスト自体が未完成・スタブのまま

**実装の問題**
- 関数が存在しない・未実装
- ロジックの誤り
- 依存モジュールの呼び出し方が正しくない

**判断できない**
- テストと実装の両方に問題がある可能性
- 実行環境の問題（パスが通っていない・依存が未インストール等）

### 5. Bug 修正タスクの実環境確認（Bug タスクのみ）

タスクイシューが Bug 修正タスク（親が `[Bug]` イシュー）である場合、
テスト GREEN に加えて以下の実環境確認を実施する。

1. バグイシューの本文・再現テストを読み込み、再現手順を把握する
2. 再現手順をモックなしで実行し、エラーが発生しないことを確認する
3. 確認結果をイシューにコメントする：

   **確認できた場合（バグ修正を確認）:**
   ```
   [実環境確認 OK]
   再現手順を実行: エラーなし（バグが修正されていることを確認）
   ```

   **実環境確認が不可能な場合（環境依存・ネットワーク不可・外部サービス依存等）:**
   ```
   [実環境確認 スキップ]
   理由: <確認不可の理由>
   判断をユーザーに委ねます。
   ```

> **注意**: 実環境確認がスキップの場合は `[Auditor GREEN]` を自動で記録しない。
> ユーザーの判断コメントを受けてから GREEN を記録すること。

---

### 6. 別タスクスコープのバグ発見時：バグイシューを発行

エラーが現在のタスクスコープ外（別タスク・別機能の問題）と判断した場合、
まず同内容のオープンな `bug` イシューが既に存在しないか確認する（`search_issues` の `label:bug` + キーワード）。

**既存イシューが見つかった場合**: 新規発行せず、既存イシューへ重複検知コメントを追加する
（`workflow/docs/spec/issue-triage.md` 3節のプロトコル、`<!-- hot-issue-dup -->` マーカー必須）：

```bash
gh issue comment <既存イシュー番号> \
  --body "## 重複検知 ($(date +%Y-%m-%d))
<!-- hot-issue-dup -->
検知元: xp_Auditor（タスク #<現在のタスクイシュー番号>）
同内容の失敗を再検知しました。"
```

現在のイシューにも記録する：
```
[Bug イシュー重複検知 #<既存イシュー番号>]
別タスクスコープのバグを検出。既存イシュー #<番号> に重複検知コメントを追加済み。
現タスクのテスト結果には影響しない。
```

**見つからない場合**: 新規バグイシューを起票する：

```bash
gh issue create \
  --title "[Bug] <バグの概要>" \
  --body "## 発見経緯
タスク #<現在のタスクイシュー番号> の Auditor チェック中に発見。

## エラー内容
<エラーメッセージ・再現条件>

## 影響範囲
<どのタスク・機能に関係するか>

## 関連イシュー
#<現在のタスクイシュー番号>

## 親ストーリー
#<親ストーリーイシュー番号>

## 親ブランチ
feature/issue-<親ストーリーイシュー番号>" \
  --label "bug,epic/<epic名>"
```

発行後、現在のイシューにも記録する：
```
[Bug イシュー発行済み #<番号>]
別タスクスコープのバグを検出。新規イシュー #<番号> として登録済み。
現タスクのテスト結果には影響しない。
```

### 7. イシューにステージコメントとして結果を記録

GREEN の場合：
```
[Auditor GREEN]
PASS: n件 / テストコマンド: `<コマンド>`
```

RED の場合（同一タスクスコープ）：
```
[Auditor RED]
FAIL: n件

### FAIL 分析

**[テスト名]**
- エラー: `<エラーメッセージ抜粋>`
- スコープ: 同一タスク内
- 判断: テスト設計の問題 / 実装の問題 / 判断不能
- 根拠: <なぜそう判断したか>
```

### 8. サブイシュー完了時の親イシューへの完了報告

[Auditor GREEN] をサブイシューに記録した後、親イシューに完了報告コメントを行う：

```
サブイシュー #<番号> 完了。残り: #<番号>, #<番号>
```

GREEN 確認後、親イシューへ完了コメントを書き込む（`gh issue comment <親イシュー番号>`）。
全サブイシューが完了した場合は、xp_Director が `xp_Auditor test <epic> <story>` を呼ぶ（Story-level Auditor フェーズ）。

### 9. xp_Director に結果を返す

- GREEN: 完了として返す
- RED（同一タスクスコープ）: 原因・該当箇所を添えて返す → Director が implement に差し戻す
- 別タスクバグ発見: バグイシュー番号を添えて「バグイシュー発行済み」として返す → Director が通常キューで処理

## 処理フロー（doc モード）

### 1. docs/ 以下の生成物を確認

- specディレクトリの `README.md` の索引整合性
  - specディレクトリは `xp_doc_spec` と同じ優先順位で解決する：1（優先）`api/<EpicName>/docs/spec/` が存在する場合はそちら、2（フォールバック）`<EpicName>/docs/spec/`
- 各ドキュメントの内容が薄すぎないか

### 2. issue2md ログの存在・鮮度を確認

`xp_Documenter` の手順1で `xp_issue2md` が実行されているはずだが、欠落・陳腐化することがあるため検証する。

1. 対象イシュー番号・エピック名から対象パスを導出する（`xp_issue2md` と同じ判定方法）：
   - ラベル `epic/<EpicName>` からエピック名を判定する
   - 無い場合はイシューのタイトルや親イシューのラベルを参照する
   - 対象パス: `<EpicName>/docs/issues/issue-<issue_number>.MD`
2. ファイルが存在するか確認する → 存在しなければ **欠落（NG）**
3. 存在する場合、ファイル内のコメント件数・最終コメントの日時を GitHub イシュー側の実際のコメント件数・最新コメント日時と比較する → 一致しなければ **陳腐化（NG）**
4. 一致すれば **OK**

### 3. イシューにチェック結果をコメント

```
[Auditor ドキュメントチェック中]

### ドキュメントチェック結果
- spec/README.md: <OK / NG: 理由>
- spec/<領域>.md: <OK / NG: 理由>
- reference/: <OK / NG: 理由>
- issue2mdログ: <OK / NG: 欠落 / NG: 陳腐化（GitHub上 n件 / ログ上 m件）>
```

### 4. OK の場合: xp_Director に OK を返す

PR 発行は xp_Director の責務。
結果のみ返す：
```
[Auditor doc OK]
xp_Director がPRを発行します。
```

### 5. xp_Director に結果を返す

- OK: `[Auditor doc OK]` を記録して Director に返す。PR発行は Director の責務
- NG（spec/reference 等）: 問題点を添えて返す
- NG（issue2mdログの欠落・陳腐化）: 「issue2mdログ NG」として、**xp_Documenter による `xp_issue2md <issue_number>` の再実行が必要** であることを明記して返す
  ```
  [Auditor doc NG: issue2mdログ]
  対象: <EpicName>/docs/issues/issue-<issue_number>.MD
  理由: 欠落 / 陳腐化（GitHub上 n件 / ログ上 m件）
  xp_Director は xp_Documenter に issue2md の再実行を差し戻してください。
  ```

---

## 注意事項

- **ファイルを編集しない**。Read ツールでの参照のみ許可
- **直接テストコマンドを実行しない**。必ずスキル経由で実行する
- GREEN 偽装（テスト削除・スキップ追加）は Auditor の役割ではなく、発見した場合はコメントで報告する
- 同じ RED が繰り返される場合（前回コメントと同じ失敗）は、その旨を記録して xp_Director に報告する
- 別タスクスコープのバグはサイレントスキップ禁止。必ずバグイシューを発行するか、既存イシューへ重複検知コメントを追加する
