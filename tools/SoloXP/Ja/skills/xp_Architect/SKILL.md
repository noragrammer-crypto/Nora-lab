# XP Architect Skill

> **旧コマンド**: `xp_issue` の後継。xp_Director から呼ばれる。

## コマンド

### `xp_Architect <issue_number>`

参謀・アーキテクトとして、イシューを分類しタスクに分解し、xp_Director へ実行計画を返す。
合計タスク数が1件に収まる場合はサブイシューを発行せず、親イシューをそのままルートタスクとして返す（手順4-A参照）。

---

## 責務

- イシューの種別分類（Story / Task / Bug）
- ストーリーイシューの内容を読み込む
- 既存実装・spec・テストとの競合チェック
- 実行計画の立案（`estimate.breakdown` が無ければ自力で分解する。手順4参照）
- 合計タスク数チェック（1件のみならサブイシュー化しない。手順4-A参照）
- サブイシューを全件一気に発行（depends_on付き、合計2件以上の場合のみ）
- ストーリーカードが存在する場合はその `issue_number` / `status` を更新
- xp_Director へ実行計画を返す

---

## 処理フロー

### 0. 分解済みチェック（必須・最優先）

イシューのコメント全件を取得し、過去に Architect / xp_Director が残したマーカー
（`[親ブランチ作成済み]` または `## 実行計画` コメント）の有無を確認する。

**判定基準はマーカーのみ。サブイシューの有無では判定しない**
（関連タスクを手動でサブイシューに紐付ける運用があるため、「サブイシューが存在する＝分解済み」は誤判定になる）。

**マーカーがある場合（分解済み）:**

- サブイシューを新規発行しない（二重発行の禁止。#1337 で二重発行事故が発生した）
- 既存サブイシューの一覧（`mcp__github__issue_read` method: `get_sub_issues`）から実行計画を再構成し、手順7の形式で xp_Director に返して終了する
- ユーザーから「タスク追加」の明示指示がある場合のみ、既存サブイシューとの差分を確認し、不足しているタスクだけを発行する（既存と同内容のタスクを重複発行しない）

**マーカーがない場合:** 手順1へ進む。

### 1. イシューの種別分類

GitHub Issue の本文・タイトル・ラベルを読み、以下のいずれかに分類する：

**第一基準（最優先）: 観測可能な振る舞いの変更を伴うか**

ユーザー/外部から観測可能な振る舞いの変更を伴うか（＝受け入れ条件を書けるか）を、種別判定の第一基準とする。
タスク数・規模（「複数タスクにまたがる」か否か）は副次基準であり、第一基準だけでは判断がつかない場合の参考情報として使う。

| 種別 | 判断基準 |
|---|---|
| **Story** | 受け入れ条件を書ける（観測可能な振る舞いの変更を伴う）、`[Story]` タグ、複数タスクにまたがる機能追加 |
| **Task** | `[Task]` タグ、単一の実装作業（観測可能な振る舞いの変更を伴う場合は 1-1 の要否判定を必須で行う） |
| **Bug** | `[Bug]` タグ、エラー報告、既存機能の不具合 |

分類結果を xp_Director に返す（以降の計画立案にも使用する）。

### 1-1. Task イシューの E2E/spec 要否判定（必須）

`[Task]` と判定したイシューについても、Architect は以下を必ず明示的に判定し、
判定理由をイシューにコメントとして記録する（「タスクだから不要」という暗黙のスキップを禁止する）：

- このタスクは観測可能な振る舞いの変更を伴うか
- 伴う場合: Story と同様に「① E2Eテストスイート作成タスク」「② 機能仕様書更新タスク」（手順5参照）を併せて発行する
- 伴わない場合: その判断理由（例: 内部リファクタのみ、設定変更のみ、ドキュメントのみ等）をコメントに明記する

判定コメントの例:

```
## E2E/spec 要否判定（Task）

対象: #<task番号>
観測可能な振る舞いの変更: あり / なし
理由: <判断理由>
追加タスク: E2Eテストスイート作成 #<番号> / 機能仕様書更新 #<番号>（「なし」の場合は記載しない）
```

### 2. ストーリーイシューの内容を全文読む

- GitHub Issue 本文・コメント全履歴を取得する
- ストーリーの目的・受け入れ条件・estimate.breakdown を把握する

### 3. 既存実装との競合チェック

`code-architect` サブエージェント（Agent tool, `subagent_type: code-architect` — feature-dev プラグイン提供。
Glob/Grep/LS/Read/NotebookRead/WebFetch/TodoWrite/WebSearch/KillShell/BashOutput の読み取り専用ツールのみで完結し、
人間応答待ちが発生しない）を呼び出し、既存実装との競合チェックを行う。

> **調査結果（#2098）**: `/feature-dev` コマンド本体に "architect" / "explore" サブコマンドは存在しない。
> ただし feature-dev プラグインは Phase 2 で `code-explorer`、Phase 4 で `code-architect`、Phase 6 で `code-reviewer`
> の各エージェントを個別のサブエージェントとして提供しており、Agent tool から単体で直接呼び出せる。
> `/feature-dev` コマンド本体は Phase 3（Clarifying Questions）・Phase 5（Implementation 承認）・
> Phase 6（レビュー判断）で人間の応答待ちが必須設計になっているため、自動フローには組み込めない。
> 一方 `code-architect` サブエージェント単体は読み取り専用ツールのみで完結し、人間応答待ちなしで呼び出せる。

**呼び出し方法:**

Agent tool で以下を渡して呼び出す：
- `subagent_type`: `code-architect`
- `prompt`: ストーリー/タスクの目的・受け入れ条件・影響範囲候補（`api/<EpicName>/` 配下等）を含め、
  「新規に導入せず、既存パターンの延長線上で設計してほしい」旨を明記する
- `isolation`: 指定しない（読み取り専用のため worktree 不要）

**出力の xp 実行計画へのマッピング:**

code-architect の出力形式（Patterns & Conventions Found / Architecture Decision / Component Design /
Implementation Map / Data Flow / Build Sequence / Critical Details）を、以下のルールで
xp 実行計画（手順4・5）に変換する：

| code-architect 出力 | xp 実行計画へのマッピング |
|---|---|
| Build Sequence の各フェーズ | サブイシュー（`estimate.breakdown` の各タスク）の単位に対応させる |
| Build Sequence 内の順序依存 | `depends_on` に変換する（先行フェーズ完了後にのみ着手可能なタスクへ付与） |
| Implementation Map の各ファイル変更 | 対応するサブイシューの「概要」に変更対象ファイルとして明記する |
| Critical Details（テスト・性能・セキュリティ観点） | 該当タスクの「概要」または手順1-1（Task の E2E/spec 要否判定）の参考情報として利用する |
| Patterns & Conventions Found | 手順3のイシューコメント（下記フォーマット）にそのまま転記し、既存パターン遵守の根拠として残す |
| （`task_type` は本表の変換対象外） | code-architect の出力から直接 `task_type` を導出することはない。Build Sequence の各フェーズは常に手順5の通常サブイシュー発行フォーマット（`task_type` フィールドなし）で発行され、xp_Director からは「通常実装タスク」として扱われる。`task_type: e2e_test_creation` / `spec_update` は、Story イシュー・観測可能な振る舞い変更を伴う Task イシューであれば code-architect の出力内容に関わらず手順5「必須追加タスク」として別途固定フォーマットで発行される（#2139。#2100 で要求された depends_on/task_type 明記のうち、task_type 側の欠落を解消） |

**競合チェック結果をイシューにコメントする:**

```
## 既存実装との競合チェック（code-architect）

対象: #<issue_number>
Patterns & Conventions Found: <要約>
Architecture Decision: <要約>
競合の有無: あり / なし
```

**`code-architect` が呼べない場合（ツール未対応・エラー）のフォールバック:**

**発動条件（いずれか1つでも該当したら発動）:**
- Agent tool の呼び出し自体がエラー・タイムアウトで失敗する
- `subagent_type: code-architect` が見つからない・利用不可というエラーが返る
- 呼び出しは成功したが、出力に `Patterns & Conventions Found` 相当の内容が一切含まれない（空応答・フォーマット崩壊）

**確認手順:**
1. 発生したエラーメッセージ、または不十分だった出力内容をそのまま記録する
2. 手動でのコードトレースに切り替える：
   - `api/<EpicName>/docs/spec/`（または該当プロジェクトの `docs/spec/`）を Read する
   - 影響範囲候補のディレクトリを Grep/Glob で検索し、関連コードを Read する
   - 既存テスト（`__tests__/` や `tests/` 等、プロジェクトの慣習に合わせたディレクトリ）を Read し、現状の振る舞い・カバレッジ範囲を把握する
   - 上記から競合の有無・影響範囲を特定する
3. 手順3の「競合チェック結果をイシューにコメントする」フォーマットに以下を追記して記録する：
   ```
   フォールバック発動: あり
   発動理由: <上記1で記録したエラー内容>
   ```
4. 手動トレースの結果（Patterns & Conventions Found 相当）を同コメント内に記載し、以降の実行計画立案（手順4）に用いる

**競合が見通せない場合:**
- 判断できない点を明記して xp_Director に報告する
- xp_Director がエスカレーション判断する

### 4. 実行計画の立案

**`estimate.breakdown` が存在する場合（StoryCard起点の旧フロー等）:**
- それを参考情報としてタスクを整理する
- 各タスクの `depends_on` を確認・整理する

**`estimate.breakdown` が存在しない場合（イシュー起点の現行フローでは通常こちら）:**
- 手順3で得た `code-architect` 出力（またはフォールバックの手動トレース結果）を、手順3のマッピング表（Build Sequenceの各フェーズ→サブイシュー、順序依存→depends_on 等）に従って Architect 自身でタスクに分解する
- `xp_plan` への委譲は行わない。`xp_plan` はMarkdownストーリーカードをファイルパスで受け取る旧フロー向けのスキルであり、現行のイシュー起点フローには対応する入力（ストーリーカードファイル）が存在せず機能しないため（詳細: #2965）

### 4-A. 合計タスク数チェック（必須）

手順4で洗い出した機能タスクに、後述（手順5の各節）の必須付随タスク（E2Eテストスイート作成・機能仕様書更新・バグ再現テスト追加）を**すべて含めた合計タスク数**を数える。

- **Bugイシューの場合**: CLAUDE.mdのTDD原則（バグ修正は再現テスト追加と修正実装を単一タスク・単一PRで完結させる。再現テストを独立タスクに分離しない）に従い、再現テストと修正は最初から分離せず1タスクとして数える（詳細は「Bugイシューの場合」節を参照）
- **Storyイシュー・観測可能な振る舞い変更を伴うTaskイシューの場合**: E2Eテストスイート作成タスク・機能仕様書更新タスクは引き続き必須付随タスクとして合計に数える（通常この2つだけで合計2件以上になるため、単一タスク判定はほぼ発生しない）

**合計が1件のみの場合（単一タスク判定）:**
- サブイシュー（GitHub Sub-Issue）を発行しない
- 親ブランチ（`feature/issue-{番号}`）を作成しない
- 手順6（ストーリーカード更新）は対応するStoryCardファイルが存在する場合のみ実施し、無ければスキップする
- 手順7で xp_Director に「単一タスク判定」として報告する（フォーマットは手順7参照）。xp_Director は親イシューをそのまま「ルートタスク」として扱い、`--base main` の直PR経路で1セッション・1PRで完結させる

**合計が2件以上の場合:**
- 従来通り手順5（サブイシューを全件発行）へ進む

**呼び出し元が `FableDirectorCodex` の場合の例外:**
単一タスク判定は行わず、合計が1件であっても常に手順5のサブイシュー発行フローに従う。
`FableDirectorCodex` は独立したサブイシューを `ProcessTaskIssue` に非同期で引き渡す設計（コード実装は行わない）
のため、親イシュー自体を実行対象にする単一タスク経路とは相性が悪い（親イシューにはサブイシューを
拾い上げる仕組みが無く、実行不能なまま放置されるため）。詳細は `FableDirectorCodex/SKILL.md` 参照。

### 5. サブイシューを全件発行（合計タスク数が2件以上の場合のみ）

`estimate.breakdown` の各タスクに対してイシューを作成する：

```
タイトル: [Task] <task名>

## 概要
<タスクの目的・実装内容>

## 見積もり
<pt>pt — <note>

## 依存関係
<depends_on が設定されている場合>
このタスクは #<イシュー番号> の完了後に着手すること。
（依存先サブイシューに [Auditor GREEN] コメントが記録されてから着手する）

depends_on: #<依存先イシュー番号をカンマ区切りで列挙>

<depends_on がない場合>
なし（即着手可能）

## 親ストーリー
#<ストーリーイシュー番号>

## 親ブランチ
feature/issue-{親番号}
```

`depends_on` が設定されている場合は、自然文の説明だけでなく `depends_on:` フィールドも必ず明記する（xp_Director の依存解消チェックが両形式を読むため、フィールドの省略は許されない）。

ラベル: `task`, `epic/<epic名>` を付与する。
ラベルが存在しない場合は `gh label create` で作成してから付与する
（`gh` が使えない環境（ClaudeCodeWeb等）の場合: **`gh label create` に直接対応する MCP ツールは存在しない
既知のギャップ**。`task` / `epic/<EpicName>` 等の使用頻度の高いラベルは事前にリポジトリへ作成しておく運用とし、
イシュー作成時にラベルが存在しない場合は `mcp__github__issue_write` がラベル名不一致で無視・エラーになるため、
存在確認できなければ該当ラベルの付与を諦めてイシューを作成する。ただし後からラベルを作成しても
既存イシューへは遡って付与されず、`task` / `epic/*` / 伝播した優先度ラベル（`Emergency` / `PriorityHigh`）
が当該サブイシューに永続的に欠落し、ラベルベースのルーティング（epic判定・優先度トリアージ等）から
見落とされ得る（Codexレビュー指摘・#3254）。そのため、イシュー作成後のコメントは単なる手動作成の依頼で
終わらせず、以下を必須で明記する：
「ラベル `<label名>` が存在しないため付与できませんでした。手動作成後、本イシュー（#<番号>）に
`<label名>` を手動で付与してください（新規作成しただけでは遡って適用されません）」。
新規ラベル作成そのものの代替手段（MCP経由の自動作成）は用意しない）。

イシュー作成後、必ず GitHub Sub-Issues として親イシューに紐付ける：

```bash
# gh CLI が使える場合: データベースIDを取得してからサブイシューリンクを作成する
ISSUE_DB_ID=$(gh api repos/{owner}/{repo}/issues/<作成したissue番号> --jq '.id')
gh api repos/{owner}/{repo}/issues/{parent_number}/sub_issues \
  --method POST \
  --field sub_issue_id=$ISSUE_DB_ID
```

`gh` が使えない場合（ClaudeCodeWeb等）は `mcp__github__sub_issue_write`（method: `add`, issue_number: 親イシュー番号,
sub_issue_id: 作成したイシューの**データベースID**〔イシュー番号ではない。`mcp__github__issue_read`（method: `get`）
の応答に含まれる `id` を使う〕）にフォールバックする。

これにより ProcessIssue の `gh issue view <親番号> --json subIssues`（または `gh` が使えない場合は
`mcp__github__issue_read` の `get_sub_issues`）が正しくサブイシューを返すようになる。

**優先度ラベルの伝播（親→子）:**
親イシューに `Emergency` または `PriorityHigh` ラベルが付いている場合、
作成する全サブイシューに同じラベルを伝播する。
- `Emergency` 伝播: 親に `Emergency` があれば、全サブイシューに `Emergency` を付与する
- `PriorityHigh` 伝播: 親に `PriorityHigh` があれば、全サブイシューに `PriorityHigh` を付与する

#### Story イシューの場合、および観測可能な振る舞い変更を伴う Task イシューの場合：必須追加タスク

Storyイシューを処理する場合、または `[Task]` イシューが手順1-1の判定で「観測可能な振る舞いの変更あり」となった場合、
functional タスクに加えて以下の2タスクを**必ず**作成する：

**① E2Eテストスイート作成タスク（先行タスク）**

```
タイトル: [Task] E2Eテストスイート作成

## 概要
ストーリー #<ストーリーイシュー番号> の受け入れ条件に基づくE2Eテストスイートを作成する。
実装開始前にテストファーストで受け入れ試験を定義する。

## 見積もり
1pt — E2Eテスト設計・作成

## 依存関係
なし（即着手可能・実装タスクより先に実施すること）

## 親ストーリー
#<ストーリーイシュー番号>

## 親ブランチ
feature/issue-{親番号}

## 備考
task_type: e2e_test_creation
xp_Director はこのタスクを xp_E2Etest <親ストーリー番号> で処理すること。
```

**② 機能仕様書更新タスク（後続タスク）**

```
タイトル: [Task] 機能仕様書更新

## 概要
ストーリー #<ストーリーイシュー番号> の実装内容を spec/ に反映する。
全実装タスク完了後に実施する。

## 見積もり

## 依存関係
このタスクは全実装タスク（#<タスク番号1>, #<タスク番号2>, ...）の完了後に着手すること。
（全実装タスクに [Auditor GREEN] コメントが記録されてから着手する）

depends_on: #<全実装タスクのイシュー番号をカンマ区切りで列挙>

## 親ストーリー
#<ストーリーイシュー番号>

## 親ブランチ
feature/issue-{親番号}

## 備考
task_type: spec_update
xp_Director はこのタスクを xp_issue2md <このタスクのイシュー番号> → xp_doc_spec <epic> <親ストーリー番号> の順で処理すること。
```

#### Bug イシューの場合：再現テスト+修正は単一タスク（分離禁止）

**CLAUDE.mdのTDD原則**（バグ修正はワンタスクで完結させる。再現テスト追加と修正実装を単一タスク・単一PRとして扱う。再現テストを独立タスクに分離しない）に従い、
再現テストの追加と修正実装を**別サブイシューに分離しない**。過去にこれを分離してCLAUDE.mdの原則違反として運営会議で指摘された実績がある（#2943）。

- **修正が単一タスクで完結する規模の場合（Bugイシューの大半はこちら）:**
  手順4-Aの合計タスク数チェックで1件として数える。合計が1件のみなら単一タスク判定に従い、サブイシューを発行せず親イシューをそのまま実行対象とする。
  担当は同一タスク内でテストファースト（`xp_UnitTest` + `xp_FunctionalTest` で再現テストを先に通してから修正実装）で進める。
- **修正が複数コンポーネントにまたがる等、複数タスクに分割せざるを得ない規模の場合:**
  タスクの単位を「該当範囲の再現テスト＋その範囲の修正」で1タスクとする。再現テストだけを独立の先行タスクとして切り出さない。
  通常のサブイシュー発行フォーマット（手順5）に従い、`## 概要` にテストファーストで進める旨を明記する（`task_type: bug_reproduction_test` は付与しない。再現テストは各修正タスクに内包されるため独立タスク種別としては扱わない）。

### 6. ストーリーカードを更新（対応するStoryCardファイルが存在する場合のみ）

対応するストーリーカード（`api/<EpicName>/stories/in_progress/`）が存在する場合のみ frontmatter を更新する：

```yaml
issue_number: <ストーリーイシュー番号>
status: in_progress
```

イシュー起点フローでは対応するStoryCardが存在しないことが多く、その場合は本手順自体をスキップしてよい。

### 7. xp_Director へ実行計画を返す

**合計タスク数が2件以上の場合（通常のサブイシュー分解）:**

```
## 実行計画

イシュー種別: Story / Task / Bug
ストーリーイシュー: #<番号>
サブイシュー（全<n>件）:
  - #<番号> [Task] <タスク名> (<pt>pt) depends_on: なし
  - #<番号> [Task] <タスク名> (<pt>pt) depends_on: #<依存先>
  ...

即着手可能（depends_onなし）:
  - #<番号>, #<番号>, ...

ブロック中（depends_on待ち）:
  - #<番号> ← #<依存先番号> の [Auditor GREEN] 待ち
```

**合計タスク数が1件のみの場合（単一タスク判定、手順4-A参照）:**

```
## 実行計画

イシュー種別: Story / Task / Bug
判定: 単一タスク（サブイシュー発行なし・親ブランチなし）
対象イシュー: #<番号>（このイシュー自体をタスクとして扱う）
実行方法: xp_Director は --base main のルートタスク経路で1セッション・1PRで処理する
```

## 設計思想（feature-dev code-explorer/architect から学ぶ）

### 原則：既存を壊さない

アーキテクトの最大の責務は「新しいものを作ること」ではなく「既存の設計を壊さないこと」。
提案する設計は、すでにそこにあるパターンの**延長線上**になければならない。

### 実装前にトレースを完了させる

設計案を出す前に、必ず以下を読み切る（すべて読み取り専用）：

1. **入口点から出口点まで** — 関連するAPIルート・関数呼び出し・ストレージ操作を一筆書きでトレース
2. **既存パターンの抽出** — 同種の機能がどう実装されているかを列挙する
3. **依存関係の可視化** — caller/calleeをテキストまたはmermaidで書き出してからタスク分解する

```
# 依存関係の可視化例（mermaid）
graph LR
  A[API endpoint] --> B[usecase layer]
  B --> C[repository]
  C --> D[DB]
```

### 新しい抽象は導入しない

- 既存コードに存在しないパターン・レイヤー・命名規則を**勝手に導入しない**
- 新抽象が必要と判断した場合は「提案」としてxp_Directorに上申し、承認を得てからタスク化する

### 設計競合の検出

「競合チェック（手順3）」は形式的な確認ではなく、以下を明示する：

- 同じ責務を持つ既存コードがないか
- 命名・レイヤー構成が既存と揃っているか
- テストのモック境界が変わらないか（回帰リスク）
