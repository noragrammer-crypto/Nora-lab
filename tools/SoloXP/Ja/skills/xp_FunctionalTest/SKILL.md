# XP Functional Test Skill

## コマンド

### `/xp_FunctionalTest <#issue番号>`

タスクイシューを読み込み、複数の関数・モジュールにまたがる
機能テスト（Functional Test）スイートを作成する。

> **呼び出し元**: xp_Director から呼ばれる。GitHub Issue から生成する。

---

## 動作手順

### 1. タスクイシューを読み込む

- GitHub Issue の内容・コメントを取得する
- 以下を把握する：
  - 実装対象の機能・処理フロー
  - 親ストーリーイシュー（リンクがあれば参照）
  - 関連するソースファイル
  - エピック名（`epic/<EpicName>` ラベルから取得）

### 2. 対象コードを調査

- タスクに関連するソースファイルを特定して読み込む
- モジュール間の依存関係・データフローを把握する
- テスト可能な入出力の境界を特定する

### 3. 機能テストスイートを作成

単体テストより大きく、E2E より小さい粒度。
複数の関数・クラスが連携して正しく動作することを検証する。

```
api/<EpicName>/tests/functional/
└── <task_name>.test.<ext>
```

テストケースの観点：
- 正常系フロー（主要なデータフロー全体）
- 異常系フロー（エラーハンドリングの連鎖）
- 境界値・エッジケース
- モジュール間のインターフェース

### 4. イシューにコメントで報告

```
## 機能テストスイート作成完了

テストファイル: `api/<EpicName>/tests/functional/<task_name>.test.<ext>`
テストケース数: <n>件

カバー範囲:
- <モジュール名>: <検証内容>
...
```

---

## 注意事項

- 外部 API・DB は必要に応じてモック/スタブを使用する
- テスト対象のコードがまだ存在しない場合は、インターフェースを仮定してテストを書く
- `/xp_UnitTest` との重複を避け、モジュール間連携にフォーカスする
- SKILL.md 等のドキュメント文言・見出し番号を `toContain`/正規表現でそのままアサートしない。検証するのは構造・契約（必須セクションの存在、frontmatterスキーマ、参照ファイルの実在等）に留める（SoloXP/docs/spec/tdd_principles.md 原則7）
