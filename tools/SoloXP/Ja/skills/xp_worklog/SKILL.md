# XP Worklog Skill

## コマンド

### `/xp_worklog <storycard_path または #issue番号>`

指定したストーリーイシュー（およびサブイシュー）の
作業時間コメントを集計してレポートし、`worklog/` に保存する。

### `/xp_worklog`（引数なし）

直近クローズされた Issue を全件集計して
イテレーションレポートを表示し、`worklog/` に保存する。

---

## 作業時間コメントのフォーマット

以下の形式のコメントを作業ログとして認識する：

```
作業開始 <timestamp>
作業完了 <timestamp> / 所要時間: XX分
tokens: prompt=XXXk completion=XXXk total=XXXk
model: <model-id>
作業中断 <timestamp>
作業再開 <timestamp>
```

`<timestamp>` は以下の2形式のいずれかを認識する（新形式が正、旧形式はlegacy互換）：

- **新形式（正）**: オフセット付きISO 8601 `YYYY-MM-DDTHH:mm:ss+09:00`。`workflow/lib/get-jst-timestamp.js`
  の `getCurrentJstTimestamp()`（またはCLIラッパー `workflow/scripts/get-jst-timestamp.js`）で
  ランタイムから機械取得し、Asia/Tokyoへ変換した値。LLM自身が現在時刻やUTC→JST変換を推測してはならない
  （#3279/#3281）
- **旧形式（legacy）**: `YYYY-MM-DD HH:MM JST`。`JST` 明記のない過去のタイムスタンプはUTCとして解釈する
  （後方互換。新規記録では使わない）

- `作業開始` → `作業完了` で1セッションの所要時間を計算する（新形式・旧形式が混在していてもタイムゾーンを揃えてから差分を計算する）
- `作業中断` / `作業再開` がある場合は中断時間を除外して計算する
- `所要時間: XX分` が明記されている場合はその値を優先する
- `tokens: prompt=XXXk completion=XXXk total=XXXk` は `作業完了` 行の直後に付記される（省略可）
- `model: <model-id>` は `tokens:` 行の次行に付記される（省略可）
- `tokens:` 行のフォーマットが崩れている場合はユーザーに確認する（自動補完しない）

### トークン消費の集計ルール

- `tokens:` 行から `prompt=XXXk`、`completion=XXXk`、`total=XXXk` の値をパースする
  - `k` サフィックスはキロトークン単位（例: `350k` → 350,000 tokens）
  - `k` サフィックスがない場合はそのまま整数として扱う
- 複数セッションにまたがるイシューはトークン消費を**合算**する
  - 一部のセッションにのみ `tokens:` 行がある場合（混在イシュー）: `tokens:` 記録があるセッションの値のみを
    合算して表示し、記録のないセッションがあることを備考等に付記する（例:
    `prompt=120k completion=30k total=150k（一部セッション未記録）`）。記録のないセッションがあることを
    理由に、他のセッションの記録済みトークン消費まで「記録なし」扱いにして捨てない（#2180）
- イシュー内の**全セッション**で `tokens:` 行が存在しない場合のみ、そのイシューを「記録なし」として表示する
  （「作業時間コメントが存在しないIssue」と同じ扱い）

### タイムスタンプが未記録の場合

初期のイシューで開始時間・終了時間が記録されていない場合:
- GitHub コメントのタイムスタンプ（`createdAt`、UTC）を参考に推定値を生成する
- 最初のコメントの `createdAt` を開始時間として使用する
- 最後のコメントの `createdAt` を終了時間として使用する
- 推定値は記録ファイル内で `(※推定)` と明記する
- フォーマットが崩れているコメントはユーザーに確認する（自動補完しない）

## 動作手順

集計フローは以下の3ステップの順で実行する（①②③）。**イシュー本文・コメントの直接取得
（データ取得）は「MD上書き更新」ステップに限定する。** イシュー番号を絞り込むためのメタデータ検索
（`search_issues` によるタイトル・ラベル・更新日時の取得のみ）はこの制約の対象外
——このメタデータ検索を省くとMD更新対象を特定できずフロー自体が成立しないため、必須の前提として許可する。

### 引数ありの場合

#### ①先週更新イシューの特定

- 実行開始時刻を記録する（⑤で使う。この時刻を基準に次回の対象範囲を決定するため、
  ①の検索より前、実行の最初に取得しておく）
- ストーリーカードの `github_issue` または指定イシュー番号から、対象ストーリー・サブイシューの番号一覧を確認する
- `worklog/worklog_timestamp.md` の最終実行日時を確認し、`search_issues` の `updated:>=<前回実行日時>`
  （メタデータ検索。本文・コメントは取得しない）で先週更新があったイシューに絞り込む（初回実行・
  記録がない場合は対象期間の週初を起点とする）
- open のまま放置されているイシューも、更新があればこの絞り込みで対象になる
- この検索結果に含まれる `state`・`closedAt` のメタデータも合わせて保持しておく（引数なし時の
  クローズ集計フィルタで使用。⑤で使う実行開始時刻と同様、この実行中のみ保持する一時データで
  MDファイルには書き込まない）
- この段階ではイシュー番号の特定のみを行う（イシュー本文・コメントの取得は次のステップに委ねる）

#### ②xp_issue2md によるローカルMD上書き更新

- ①で特定した対象イシューそれぞれに対して `xp_issue2md <issue_number>` を実行し、
  `<EpicName>/docs/issues/issue-N.MD` を最新の内容で上書きする
- **対象ストーリー配下でまだローカルMD（`issue-N.MD`）が存在しないイシューがあれば、①の
  `updated_at` 絞り込みに関わらず無条件で `xp_issue2md` を実行する。** ①の絞り込みは「先週
  更新があったイシュー」のみを対象にするため、過去に `xp_issue2md` の対象から漏れた（例: 過去の
  運用で明示的にスキップされた）古いイシューはこの絞り込みだけでは永久にMD化されない。その状態で
  ③に進むと「ファイルが存在しない＝作業時間ゼロ」として扱われ、ストーリー全体の作業時間を
  過小評価してしまう
- **イシュー本文・コメントの取得（直接データ取得）はこのステップに限定する。** 集計のために API から直接
  本文・コメントを取得する処理は行わない（issue2md の起動時間問題で最終的な内容にならないケースをこの
  再実行で解消する）

#### ③ローカルMDからの作業時間集計

対象ストーリー配下の既存 `<EpicName>/docs/issues/issue-N.MD` **全件**を読み込み、
`## コメント` セクション内の作業時間コメントから所要時間・トークン消費を集計する。
**②で更新されたファイルに限定しない。** ②は①で対象になった（先週更新があった）イシューのMDのみを
上書き更新するため、更新不要だった既存ファイルもそのまま集計対象に含める（②のリフレッシュ対象から
漏れた子イシューを除外すると、ストーリー全体の作業時間を過小評価してしまう）。
**GitHub API から直接コメントを取得する処理は行わない。** 集計はこのローカルMD読み込みのみで完結させる。

```
## ワークログレポート

ストーリー: #<番号> <タイトル>
期間: <最初のログ日付> 〜 <最後のログ日付>

### サマリー
合計時間: <n>h <m>分
見積もり: <total>pt（1pt ≈ 半日〜1日）

### イシュー別内訳

| イシュー | タイトル | 時間 | トークン消費 |
|---|---|---|---|
| #<番号> | <タイトル> | <n>h <m>分 | prompt=Xk completion=Xk total=Xk |
...
（全セッションで `tokens:` 行がないイシューのみ「記録なし」と表示する。一部セッションのみ記録がある
イシューは記録済みセッション分を合算し、未記録セッションがあることを付記する）

### 作業ログ詳細

#### #<番号> <タイトル>
| 日時 | 所要時間 | 備考 |
|---|---|---|
| YYYY-MM-DD | <n>分 | <中断あり等> |
...
```

#### 4. worklog ディレクトリへの保存

集計結果を `worklog/YYYY/MM/<epic名>.md` に保存する。

**エピック名の判定:**
- イシューのラベルから `epic/<EpicName>` パターンを探す
- ラベルに含まれる日本語接尾辞（拡張・改善・修正等）は除去する
- リポジトリルートのディレクトリ名と前方一致で突合する
- エピックラベルがない場合は `misc` を使用する

**保存ファイルのフォーマット:**

```markdown
# <Epic名> — YYYY年MM月 作業記録

## サマリー
- 合計作業時間: Xh Ym
- 完了Issue数: N件（tokens記録あり: M件）
- 総トークン消費: Xk（Issue単位平均: Yk/issue）

## イシュー別記録

| Issue | タイトル | 開始時間 | 終了時間 | 作業時間 | トークン消費 | 備考 |
|-------|---------|---------|---------|---------|------------|------|
| #123  | タスク名 | YYYY-MM-DD HH:MM | YYYY-MM-DD HH:MM | XXm | prompt=Xk completion=Xk total=Xk | |
| #124  | タスク名 | YYYY-MM-DD HH:MM | YYYY-MM-DD HH:MM | XXm | 記録なし | (※推定) |
```

- 同じエピック・同じ月のファイルが既に存在する場合は、既存のイシュー行を保持しつつ新しいイシューを追加・更新する（マージ更新）
- 月をまたぐイシューは、各月のファイルにそれぞれ記録する

#### 5. worklog_timestamp.md の更新

実行完了後、`worklog/worklog_timestamp.md` へ**最終実行日時**を記録する。**記録する値は①で
取得した実行開始時刻であり、実行完了時刻ではない。** 実行中（①〜④の処理中）に対象イシューへ
新しいコメントが追加された場合、そのコメントの更新日時は実行完了時刻より前になり得るため、
完了時刻を基準にすると次回の `updated:>=` 範囲から漏れて永久に取りこぼされる。実行開始時刻を
記録すれば、実行中に発生した更新は次回の `updated:>=<今回の開始時刻>` に含まれる（範囲が
わずかに重複するが、②のissue2md再実行は冪等なため実害はない）。次回実行時は、この
**前回実行日時（＝前回の開始時刻）**を基準に `updated:>=` で対象範囲（①）を決定する
（イシュー番号ベースのカーソルは使わない）。

```markdown
| 実行日時（開始時刻） | 処理件数 | 備考 |
|---------|---------|------|
| YYYY-MM-DD HH:MM | 処理件数: N件 | |
```

### 引数なしの場合（イテレーションレポート）

①〜⑤は引数あり時と同一の処理（先週更新イシューの特定 → issue2md 上書き → ローカルMD集計 →
worklog保存 → worklog_timestamp.md更新）を実行する。

**①の `updated:>=` 絞り込みと、レポート集計対象の絞り込みは別物として扱う。** ①の
`updated:>=` はあくまで「ローカルMDを最新化すべきイシュー」を特定するためのものであり、
数週間前にクローズ済みのイシューへ今週コメントが1件追加されただけでも対象に含まれる。
これをそのままイテレーションレポートの「今週クローズしたIssue」の母数にすると、対象外の週の
クローズが混入する。そのためレポート集計（③の一部）では、①で保持した `closed_at` メタデータを
参照し、**対象期間内にクローズされたIssueのみ** に絞り込んでからレポートを作成する（`closed_at`
はローカルMDには含まれないため、①のメタデータ検索結果を使う。ローカルMD読み込みで完結するのは
作業時間コメントの集計のみで、レポート対象の絞り込みには①のメタデータを用いる）。

**⑤のwatermark記録は引数あり時と異なり、実行開始時刻ではなく対象期間の境界を使う。** 引数あり時
は①の実行開始時刻をそのままwatermarkにできるが、引数なし時は定期カットオフ（例: 土曜15:00 UTC）
と実際の実行開始時刻がずれることがある（実行が遅延して開始される等）。もし実行開始時刻を
watermarkにすると、カットオフ〜実行開始の間にクローズされたIssueは、今回の実行では①の対象には
含まれるがレポート対象期間の外（`closed_at`が今回の対象期間より後）のため除外され、次回のwatermark
が「今回の実行開始時刻」になることで、そのIssueの`updated_at`は次回の`updated:>=`範囲より前になり
二度と拾われない（レポートに永久に含まれない）。そのため引数なし時は、⑤で記録するwatermarkを
「実行開始時刻」ではなく**「今回のレポート対象期間の終了境界（カットオフ時刻）」**とする。

#### オープン Issue 数の参考カウント

```bash
gh issue list --state open --json number | python3 -c "import sys,json; print(len(json.load(sys.stdin)))"
```

`gh` が使えない場合（ClaudeCodeWeb等）は `mcp__github__list_issues`（owner, repo, state: OPEN,
fields: [number]）にフォールバックする。1ページ最大100件のため、`pageInfo.hasNextPage` が true の間
`after` でページングしながら件数を積算する（`xp_issue2md`〈#3204〉で確立したパターン。#3217）。

直近の Sprint / イテレーション相当の期間を対象とする。期間の境界が不明な場合はユーザーに確認する。

```
## イテレーションレポート

期間: <開始日> 〜 <終了日>
クローズ Issue 数: <n>件
残オープン Issue 数: <n>件

### 合計作業時間
<n>h <m>分

### Issue 別サマリー

| # | タイトル | 見積もり | 実績 | トークン消費 | 差異 |
|---|---|---|---|---|---|
| #<番号> | <タイトル> | <pt>pt | <n>h | prompt=Xk completion=Xk total=Xk | <±> |
...
（全セッションで `tokens:` 行がないイシューのみ「記録なし」と表示する。一部セッションのみ記録がある
イシューは記録済みセッション分を合算し、未記録セッションがあることを付記する）

### 作業時間が記録されていない Issue

```

イテレーションレポートに含まれる全イシューを、エピック別・月別に `worklog/YYYY/MM/<epic名>.md` へ保存する。
（保存フォーマットは引数あり時と同一）

## Epic単位トークン消費集計（ROI）

引数ありレポートおよびイテレーションレポートに、Epic単位のトークン消費ROI集計を追加する。

### 集計方法

1. `worklog/YYYY/MM/<epic名>.md` ファイルを走査し、対象Epicの全月データを収集する
2. 複数月にまたがるEpicは各月ファイルのトークン消費を合算する（同一Issue番号が重複する場合は最新月のエントリを優先する）
3. `tokens:` 記録がないIssueは平均算出から除外し「記録なし」として表示する

### 算出値と出力フォーマット

- **完了Issue数**: worklogファイルに記録されたIssue行数の合計（tokens記録あり・なし両方を含む）
- **総トークン消費**: `tokens:` 記録があるIssueの `total=Xk` 値の合算
- **Issue単位平均トークン消費**: 総トークン消費 ÷ `tokens:` 記録ありのIssue数

```
### Epic単位トークン消費ROIサマリー

| Epic | 完了Issue数 | 総トークン消費 | Issue単位平均トークン消費 |
|------|------------|--------------|-------------------------|
| SoloXP | 12件 | 2,400k | 200k/issue |
| DiscordAIbot | 5件 | 800k | 160k/issue |
```

（完了Issue数はtokens記録あり・なし両方を含む。平均はtokens記録ありのIssueのみで計算する）

## 注意事項

- 作業時間コメントが存在しない Issue はその旨を表示する
- フォーマットが崩れているコメントは自動補完せずユーザーに確認する
- 見積もりとの比較は参考値として表示する（責める目的では使わない）
- `worklog/` ディレクトリが存在しない場合は自動作成する
- 年・月ディレクトリも必要に応じて自動作成する
