# XP Unit Test Skill

## コマンド

### `/xp_UnitTest <#issue番号>`

タスクイシューを読み込み、単体テストスイートを作成して実行する。

> **呼び出し元**: xp_Director から呼ばれる。GitHub Issue から生成する。

---

## 動作手順

### 1. タスクイシューを読み込む

- GitHub Issue の内容を取得する
- 実装対象の関数・クラスを特定する
- 関連するソースファイルを読む
- エピック名（`epic/<EpicName>` ラベルから取得）

### 2. 証明すべき命題を導出する

Issue タイトル・説明・受け入れ条件から、このタスクが「何を達成したことを証明すべきか」を
箇条書きで列挙する。

**例）** Issue: "gemini-2.0-flash-001 → gemini-2.5-flash へ更新"
- gemini-2.5-flash が設定されていること（肯定）
- gemini-2.0-flash-001 が残っていないこと（否定）

導出した命題をイシューにコメントする：

```
## テスト命題

Issue の要求仕様から以下を証明します：

- [ ] <命題1>（肯定/否定）
- [ ] <命題2>（肯定/否定）

上記命題に疑義がある場合はコメントしてください。
```

**この命題リストを満たすテストを書くこと。命題なきテストは書かない。**

### 3. 単体テストスイートを作成

1関数・1クラスを対象とした細粒度のテスト。

```
api/<EpicName>/tests/unit/
└── <module_name>.test.<ext>
```

各テストケースの観点：
- 正常系（代表的な入力値）
- 異常系（不正な入力・例外）
- 境界値（最小・最大・境界付近）
- 副作用の検証（状態変化・呼び出し確認）

### 4. テストを実行する

```bash
npm test / pytest / go test / etc.
```

実行結果を確認する：
- GREEN → 完了
- RED → 失敗箇所を特定し、テスト自体の誤りかコードの問題かを判断する

### 5. イシューにコメントで報告

```
## 単体テスト実行結果

テストファイル: `api/<EpicName>/tests/unit/<module_name>.test.<ext>`

結果: <PASS n件 / FAIL n件>

命題チェック:
- [x] <命題1>
- [x] <命題2>

<FAILがある場合>
失敗箇所:
- <テスト名>: <原因・コメント>
```

テストに疑念がある場合（テスト自体の設計に問題がある可能性）は
イシューにコメントして終了する。

---

## 注意事項

- モジュールの外部依存はモックに置き換える
- テスト自体が正しいかを常に疑う（実装に合わせてテストを歪めない）
- 実行に失敗した場合、テストの誤りと実装の誤りを切り分けてコメントする
- `/xp_FunctionalTest` との役割分担：単一関数の動作確認が本スキルの範囲
- SKILL.md 等のドキュメント文言・見出し番号を `toContain`/正規表現でそのままアサートしない。検証するのは構造・契約（必須セクションの存在、frontmatterスキーマ、参照ファイルの実在等）に留める（SoloXP/docs/spec/tdd_principles.md 原則7）
