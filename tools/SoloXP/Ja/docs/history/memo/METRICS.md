# Solo XP メトリクス定義

## パラダイムシフト：制約の逆転

### 従来の開発
```
制約（ボトルネック）= 人間の作業時間
    ↓
最適化対象 = 「いかに人間の時間を節約するか」
    ↓
手法 = 自動化、効率化、ツール導入
```

### Solo XP with AI
```
制約（ボトルネック）= トークン or CPUタイム
    ↓
最適化対象 = 「いかにAI/計算リソースを効率的に使うか」
    ↓
人間の時間は相対的に豊富（カフェ移動中も奉行は働く）
```

**これは完全な立場の逆転。TOC（制約理論）のAI時代版。**

## 重要メトリクス

### プライマリメトリクス（制約候補）

#### 1. トークン消費率

**測定項目**:
- Issue処理1件あたりのトークン数
- 1日のトークン消費量
- 月間上限までの残量（%）

**計算式**:
```
トークン消費率 = 当月累計消費 / 月間上限
Issue単価(トークン) = 総消費トークン / 処理Issue数
```

**最適化方向**:
- プロンプト効率化（システムプロンプト最適化）
- コンテキスト圧縮（不要な履歴削除）
- 適切なモデル選択（Haiku vs Sonnet vs Opus）
- バッチ処理での効率化

**目標値**:
- 月間消費率: < 80%（バッファ確保）
- Issue単価: < 100K tokens

#### 2. CPUタイム消費率

**測定項目**:
- Codespace稼働時間（時間/日）
- アイドル時間の割合（%）
- Issue処理1件あたりの平均時間
- 並行実行数（tmuxセッション数）

**計算式**:
```
CPUタイム消費率 = (当月累計時間 × コア数) / 月間上限
稼働効率 = 実作業時間 / 総稼働時間
Issue単価(時間) = 総稼働時間 / 処理Issue数
```

**最適化方向**:
- 待機時間削減（ポーリング間隔調整）
- 並行度調整（tmuxセッション数最適化）
- 即座シャットダウン（仕事終わったら寝る）
- 夜間停止（不要な時間帯の停止）

**目標値**:
- 月間消費率: < 80%
- 稼働効率: > 60%（アイドル時間40%以下）
- Issue単価: < 2.0h

### セカンダリメトリクス（スループット）

#### 3. Issue完了率

**測定項目**:
- 処理済みIssue数/日
- PR作成数/日
- マージ完了数/日
- Issue滞留時間（作成→完了）

**目標値**:
- Issue処理: 3-5件/日
- PR作成率: > 80%（Issue→PR変換率）
- マージ率: > 70%（PR→マージ変換率）

#### 4. 人間の介入時間

**測定項目**:
- Issue作成時間（平均）
- PR確認時間（平均）
- デバッグ介入時間（合計/日）

**目標値**:
- Issue作成: < 5分/件
- PR確認: < 3分/件
- デバッグ介入: < 30分/日

## 制約に応じた戦略マトリクス

| 制約状況 | 戦略 | 実装例 |
|---------|------|--------|
| **トークンが制約** | プロンプト効率化 | - システムプロンプト最適化<br>- 不要なコンテキスト削減<br>- Haiku優先使用<br>- 回答の簡潔化要求 |
| **CPUタイムが制約** | 稼働時間短縮 | - ポーリング間隔延長（30秒→60秒）<br>- 即座シャットダウン<br>- 夜間完全停止<br>- Android側作業増加 |
| **両方余裕** | スループット最大化 | - 並行度最大化（tmuxセッション増）<br>- 積極的なバックグラウンド処理<br>- 投機的コード生成<br>- リファクタリング自動化 |
| **両方枯渇** | 手動フォールバック | - Termux直接作業<br>- 翌月まで待機<br>- 優先度の再評価 |

## コスト効率分析

### 無料枠の実態

#### GitHub Codespaces
```
無料枠: 月120コアタイム（2コア×60時間 or 4コア×30時間）

想定消費パターン:
- 2コア、1日2時間稼働: 60時間/月 → ギリギリ
- 2コア、24時間稼働: 720時間/月 → 大幅超過
- 4コア、1日1時間稼働: 60時間/月 → ギリギリ

結論: 「仕事がある時だけ起動」が必須
```

#### Claude API（Pro会員想定）
```
無料枠: 詳細は要確認（実測値待ち）

想定消費:
- 1 Issue = 50-150K tokens
- 1日3 Issue = 150-450K tokens
- 月間 = 4.5-13.5M tokens

結論: プロンプト効率化が重要
```

### コスト最適化の優先順位

1. **CPUタイムの削減**（枯渇しやすい）
   - 即座シャットダウンの実装
   - ポーリング間隔の調整
   - 夜間停止

2. **トークンの効率化**（次に枯渇する）
   - システムプロンプトの最適化
   - コンテキスト圧縮
   - モデル選択（Haiku活用）

3. **スループットの向上**（余裕がある時）
   - 並行処理の増加
   - 自動化範囲の拡大
