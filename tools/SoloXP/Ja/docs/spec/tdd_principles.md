# Solo XP TDD開発原則

## 概要

Solo XP における開発はテスト駆動（TDD）を基本とする。
エージェントおよび開発者はここに定義された原則に従うこと。

---

## 原則一覧

### 1. バグ修正はワンタスクで完結

バグ修正はテスト作成〜GREENまでを一つのタスク・一つのPRで完結させる。
バグ再現テストと修正を別タスクに分割しない。

### 2. バグ再現テストは必ず資産化してコミット

バグを再現するテストは必ずコミットして資産化する。
「再現できた」という事実をコードとして記録する。

### 3. ワンタスクワンPR

1タスク完了ごとに1PRを発行する。
複数タスクをまとめてPRしない。

### 4. コード変更時はドキュメントを同時更新（コードが正）

実装を変更したらドキュメントも同一PRで更新する。
**コードが正**。ドキュメントはコードに追従する。

### 5. イシュー群全体から要求の積分を意識する

個別イシューだけでなく、イシュー群全体が何を求めているかを俯瞰して実装判断を行う。

### 6. テストファイル内で process.exit を使用しない

Jest テストファイル内で `process.exit()` を呼び出してはならない。
Jest ワーカープロセスが強制終了し、他のテストスイートが連鎖失敗するため。

```js
// ❌ 禁止
if (failures > 0) process.exit(1);

// ✅ Jest ネイティブの失敗メカニズムを使う
if (failures > 0) {
  throw new Error(`${failures}件のテストが失敗しました`);
}
// または expect() / it() / test() を使ったネイティブ記法
```

### 7. SKILL.md文言をアサートしない（構造・契約テストの原則）

SKILL.md の文言・見出し番号・コードブロック本文をそのまま `toContain` / 正規表現で
アサートするテストは禁止する。SKILL.md は仕様改善のたびに文言・構成を見直す対象であり、
文言テストは改善のたびに壊れる「実装の写経」になる（#1313, #1279, #1294 等で実例あり）。

**❌ 避けるべきパターン**:
- 特定の日本語文言・段落・コードブロック本文を `expect(content).toContain('...')` で固定する
- セクションを見出し番号（`### 3.` 等）に依存した正規表現で抽出する
- コードブロックの内容を文字列として丸ごと比較する

**✅ 採用すべきパターン（構造・契約の検証）**:
- frontmatter（`model:` / `persona:` 等）のスキーマ検証
- 必須セクションの「存在」検証（見出し番号ではなくキーワードの柔軟マッチ）
- 参照ファイルパスの実在確認（`fs.existsSync`）
- ドキュメント間の索引整合性（README に列挙されたファイルが実在するか等）
- 正本（`SoloXP/skills/xp_*` + `workflow/skills/*`、計38スキル）から生成された `dotfiles/.claude/skills/`・
  `.claude/skills/` 側のエントリが、対応する正本の内容と一致していることの確認（#2168/#2639/#2640 で同期方向
  反転後の表現に更新）。`.claude/skills/` には正本を持たない対象外スキル（`wiki_ingest`・`NovelGeneratorRun`
  等、約11件）も共存しているため、比較対象は正本から生成された38スキルのエントリに限定する
  （`docs/skill-files-sync.md`「対象外スキル」節参照）

**棄却・書き換え判断フロー**:
1. テストが文言・見出し番号に依存している場合、検証したい契約を再定義できるか検討する
   - 契約が「セクションの存在」なら見出しキーワードの柔軟マッチに書き換える
   - 契約が「特定の運用手順の文章そのもの」ならテストでの保証を諦め、
     SKILL.md レビュー（Auditor/人間）の責務に委ねてテストを削除する
2. 文言そのものを保証する必要がある場合（運用上どうしても外せない手順文）は
   「文言テスト」として明示的に残し、SKILL.md 変更時に同一PRで更新する運用ルールとする

### 8. 作業完了コメントにトークン消費を付記する（省略可）

`作業完了` コメントの直後に以下の行を付記することで、Issue単位のAI消費コストをGitHubタイムラインで追跡できる。

```
作業完了 YYYY-MM-DD HH:MM JST / 所要時間: XX分
tokens: prompt=XXXk completion=XXXk total=XXXk
model: <model-id>
```

- `tokens:` / `model:` は省略可（記録できた場合のみ付記する）
- `作業開始` コメントには付記しない（完了時のみ）
- フォーマットが崩れている場合は自動補完せずユーザーに確認する（タイムスタンプと同じ運用）
- `/xp_worklog` がこのフォーマットをパースしてEpic単位のROIサマリーを生成する（#1461実装後）

**フォーマット崩れの定義:**
- `tokens:` の値が `prompt=XXXk completion=XXXk total=XXXk` 形式でない
- `model:` の値が空欄またはモデルIDとして解釈できない文字列

**親イシュー:** #1461（AI開発コスト可視化 — Issue単位のトークン消費トラッキング）
