# ProcessIssue ── イシュートリアージと自動選択

## 概要

note記事「[イシュートリアージ、AIに先に喋られた話](https://note.com/noragrammer/n/n82e787b91fdb)」は、
`ProcessIssue` がオープンイシューから1件を自動選択する際の**判断基準そのもの**（どのラベルをどう使うか、
何を優先し何を後回しにするか）を言語化したものである。このドキュメントは、その判断基準を
`ProcessIssue` の実装・ラベル運用として整理し直したものである。

SoloXP自体が同梱する自動選択の入口は `xp_Director`（引数なし）だが、`xp_Director`（引数なし）自身は
選択ロジックを持たず、呼ばれると直ちに `/ProcessIssue` に処理を委譲する後方互換の入口として機能する
（実装は `SoloXP/skills/xp_Director/SKILL.md` 参照）。実際のイシュー選択ロジックは `ProcessIssue` 側に
ある。複数のワークフロー（ソフトウェア開発以外の作業も同じイシューキューで回している等）を1つの
キューで運用する場合、「選んだイシューをどのワークフローに渡すか」を決める層が必要になるが、
`ProcessIssue` はその選択ロジックと振り分け層をあわせ持つ実装例と捉えるとよい。

## ProcessIssueの役割

`ProcessIssue` の責務は次の2つに限定されている。実際の設計・実装判断は行わない。

1. **選択** ── オープンイシューリストから、今すぐ自動着手してよい1件を選ぶ
2. **振り分け** ── 選んだイシューの内容に応じて、適切なワークフロー（`xp_Director` 等）に委譲する

選択・振り分けはどちらもルールベースの機械的処理であるため、`ProcessIssue` 自身は軽量モデルで
動作させられる。実質的な設計・実装判断は委譲先のスキルが自身の裁量（宣言したモデル）で行うため、
`ProcessIssue` 側の判断精度を上げても実装品質には影響しない、という役割分担になっている。

```
オープンイシュー一覧
      ↓
[ProcessIssue] 未ブロックの1件を選択（本ドキュメント後半のラベルルール）
      ↓
[ProcessIssue] 内容に応じてワークフローへ委譲（判断はしない・振り分けるだけ）
      ↓
実際の設計・実装判断は委譲先スキルが行う
```

## カスタマイズ: ワークフロー振り分けを自分のリポジトリに合わせる

`ProcessIssue` のワークフロー振り分けは、リポジトリごとに扱う作業の種類に合わせてカスタマイズする
前提の部分である。判定条件はラベルまたはタイトル/本文のキーワードで書く。1つのリポジトリで
複数系統の作業（ソフトウェア開発以外の執筆・データ処理等）を同じイシューキューで回している場合に
特に有効になる。

判定条件を書く際のポイント：

- **ラベルによる判定を優先する。** タイトル/本文のキーワード判定はラベル付け忘れ時のフォールバック
  として使い、主判定はラベル（例: `epic/<名前>`）にする方が誤判定が起きにくい。
- **委譲先スキルにオプションを素通しする仕組みを用意しておく。** `ProcessIssue` が
  `implementer=codex` のようなフラグを受け取った場合、そのまま委譲先の呼び出しに引き渡す
  設計にしておくと、`ProcessIssue` 自体を変更せずに委譲先の挙動だけを差し替えられる。
- **ソフトウェア開発系のワークフローだけで足りる場合は、振り分け先を1つに絞ってよい。** その場合
  `ProcessIssue` は実質「イシュー選択層」だけになり、選んだイシューをそのまま `xp_Director` に
  渡すだけの薄いラッパーになる。
- **判断に迷うワークフローの組み合わせは自動実行しない。** 手動判断が必要な系統のイシューを検出
  した場合は、該当イシューにコメントして処理を止め、ユーザーの指示を待つ選択肢も用意しておく
  （自動化しすぎて意図しない作業に着手するリスクを避ける）。

## ラベルによるイシューの自動選択

ここからが note記事の中心テーマ。「選ぶ手順」自体は仕組み化できても、「どのラベルをどう付けるか」
の判断基準は暗黙知になりやすい。以下はその基準を明文化したものである。

### 優先度: 3段階の実行対象 + FIFO

実行対象になるイシューは3段階に分かれる。

| バケット | 条件 |
|---|---|
| `emergency` | `Emergency` ラベルあり（今日明日中） |
| `high` | `PriorityHigh` ラベルあり（今週中） |
| `normal` | どちらも無し（無印・古い順に淡々と） |

`emergency` → `high` → `normal` の順でバケットを処理し、**各バケット内では常にイシュー番号
昇順（古い順）で処理する。** 同じ優先度の中で「新しいか古いか」を個別に判断することはしない。
単純なFIFOにしておくことで、優先度判断のコストを「どのバケットに入れるか」の1回だけに集約できる。

### 除外の使い分け: backlog / block / ignore

選択対象から外すラベルは3種類あるが、**機械的な挙動はすべて同じ**（選択候補から外れるだけ）。
違うのは「なぜ今やらないか」という意図表明の方だけである。

| ラベル | 意味 | 再開条件 |
|---|---|---|
| `backlog` | 後回し。方針・着手方法は決まっていて、単に順番待ちしているだけ | `backlog` ラベルを外すことで再開する（除外フィルタは優先度バケット分類より先に評価されるため、`backlog` が付いたまま優先度ラベルだけ上げても選択対象には戻らない。急ぎたい場合はラベルを外した上で必要なら優先度ラベルを別途付ける） |
| `block` | 判断保留。自動で進めさせるのが危険、または自分の中でまだ決め切れていない | 時間経過ではなく、状態そのものが変わること（方針が固まる・原因が判明する等） |
| `ignore` | 意識的に無視。AIの自動レビュー指摘に納得できない場合等に、理由をコメントしてから使う「やらない」の終端 | 手動で見直すまで再開しない |

`block` を使う具体例：複数の実装方針で迷っている、原因不明のバグで探索的なデバッグが必要、
影響範囲が大きく確認なしに自走させたくない、など。

判断に迷ったときの基準は1つだけ：**「今すぐ自動着手させても大丈夫か？」** 大丈夫なら
`backlog` か無印のまま、危ないと感じたら `block`。

### 環境ラベルの二面性: 「弾く」か「縛る」か

開発環境が複数（スマホ・ブラウザ上のClaudeCode Web・GitHub Codespaces・ローカルPC等）ある場合、
同じイシューキューを複数環境から拾いに行く運用になる。このとき環境ラベル（`env/*`）は、
**同じフォーマットの中に正反対の意図が2つ同居している**点に注意する。

1. **弾く用途（非対応環境ガード）**: ブラウザ自動化を伴うタスク等、特定環境だと不安定・実行不能
   な作業に「対応できる環境」だけをラベルで明示し、非対応環境からは自動選択されないようにする。
2. **縛る用途（指定実行）**: ローカルのファイルに依存する作業や、目視確認しながら進めたい作業に
   あえて特定環境限定のラベルを付ける。これにより、指定環境でセッションを開くまで他の環境は
   手を出さずに待機する。

設計としては「ラベルなしがデフォルトで、どこでも実行可」「ラベルを付けるのは制約がある時だけ」
という運用にしておくと、両方の用途を同じラベル体系で表現できる。

### 依存関係・進行中チェックとの関係

上記の優先度・除外ラベルによる絞り込みに加えて、`ProcessIssue` は候補イシューごとに
「別スレッドで処理中でないか」（`[ProjectStatus: InProgress]` コメント）と
「依存先イシューが完了しているか」（`## 依存関係` セクション、依存先の完了マーカーの有無）も
確認してから最終的な1件を選択する。この2つは判断基準というよりは機械的な整合性チェックであり、
本ドキュメントが扱う「ラベルによる意図表明」とは性質が異なるため詳細は割愛するが、完了マーカーは
依存先が通常タスクなら `[Auditor GREEN]`、`spec_update` タスク（`xp_doc_spec` → `xp_Auditor doc`
のみを通過し `[Auditor GREEN]` は構造的に出力されない）なら `[Auditor doc OK]` を見る点だけは、
選択ロジックを自分でカスタマイズする際に見落としやすいので明記しておく。

## トリアージが「一度きりのコスト」になる理由

判断基準を毎回ゼロから考え直すと疲れる。環境ラベルの「弾く」と「縛る」、優先度の「後回し」と
「保留」――これらは一度、境界線を明文化してしまえば、次からは当てはめるだけで済む。判断のコストを
「ルールを作る一回きり」に集約できる、というのがこのラベル体系の狙いである。
