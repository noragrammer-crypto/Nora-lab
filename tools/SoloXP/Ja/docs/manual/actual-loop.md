# ソロXPの実運用ループ ── アイデアから実装・評価・次のイシューへ

## 概要

note記事「[大きい仕様は書かない。タスクに割って、順番に消化するだけでいい ―― ソロ開発のPR生産ライン「SoloXP」](https://note.com/n/n81773d3c58c0)」は、
イシューが立ってからPRが発行されるまでの**コード化フェーズ**を4段階フローとして解説している：

```
①Issueを立てる（人間） → ②タスクに分解する（AI: Architect役） →
③1タスク=1PRで実装する（AI: Tester→Implementer→Auditor→Documenter） →
④受け入れテスト → PR発行（AI＋人間）
```

これは [WORKFLOW.md](../../WORKFLOW.md) が定める運用フローそのものにあたる。しかし実際の運用では、
このコード化フェーズの**前後**にもう2つの工程があり、全体として輪になっている。このドキュメントは、
実際に何がイシューを生み、コード化されたものがどう評価され、また次のイシューへと繋がっていくかという
「外側のループ」を記録する。

## 全体ループ（6ステップ）

```
[0] アイデアを一行イシューに書く（人間）
        ↓
[1] AIと相談して実行可能な粒度に再定義する（人間+AI）
        ↓
[2] AIがイシューを起票する（AI）
        ↓
[3] コード化する（AI: note記事の4段階フロー）
        ↓
[4] PRで確認する（人間）
        ↓
[5] 出来上がったものを評価する（人間）
        │
        └── 評価から得た気づきが新しい一行イシューとして [0] に戻る
```

## 各ステップの詳細

### [0] アイデアを一行イシューに書く

思いついたことを推敲せず、ワンライン程度でまずイシューに落とす。この時点で実行可能な粒度である必要はなく、
抽象的・雑な状態のままでよい。目的は「あとで揮発させない」こと。揮発するプロンプトやメモではなく、
永続的なIssueという構造物にまず置く、という設計原則はnote記事の「プランモードとの違い」節
（計画をセッション内のメモに閉じず、Issueという永続的な単位に外部化する）と同じ発想である。

### [1] AIと相談して実行可能な粒度に再定義する

一行イシューのままでは `xp_Architect` が分解できるほど具体的でないことが多い。ここで人間とAIが対話し、
「これは何をもって完了とするか」「どこまでをこのイシューの範囲にするか」を詰める。
`ProcessIssue` / `xp_Director` が処理できる粒度（Story / Bug / Task として分類可能な粒度）まで
具体化するのがこのステップのゴール。

### [2] AIによるイシュー起票

[1] で固まった内容をAIがイシュー本文として整形し起票する（`xp_issue` 等）。
**このとき新しいイシューを別途作成するのではなく、[0] で立てた同一のイシューを本文編集で
更新する。** 新規に別イシューを作ってしまうと、[0] の粗い一行イシューがクローズも紐付けもされないまま
残り、`ProcessIssue` のFIFO選択が古い未整理のイシューを先に拾って処理してしまう事故につながるため。
やむを得ず新規イシューに切り出す場合は、旧イシューをクローズするか `Closes #<旧番号>` 等で明示的に
リンクしてから起票する。
ここで初めてnote記事の4段階フローの入口（①Issueを立てる）に乗る。

### [3] コード化（note記事の4段階フロー）

ここは既存のnote記事・[WORKFLOW.md](../../WORKFLOW.md) がそのまま解説している範囲であり、
本ドキュメントでは詳細を繰り返さない。要約すると：

②タスク分解（Architect役、Story/Bug/Taskへの分類とサブイシュー化） →
③1タスク=1PR実装（Tester→Implementer→Auditor→Documenter、TDDでRED/GREEN管理） →
④受け入れテスト→PR発行。

詳細はnote記事本体、[WORKFLOW.md](../../WORKFLOW.md)、[docs/spec/](../spec/)、
[使い方チュートリアル](./tutorial.md) を参照。

### [4] PRで確認する

実装が完了しPRが上がってきたら、人間が差分を読んで確認する。マージとイシュークローズは
基本的に人間の責務とする（自分のリポジトリの `CLAUDE.md` にPR発行の事前承認範囲を定義している
場合でも、最終的なマージ判断は人間に残す設計。詳細は [CLAUDE.md.template](../../CLAUDE.md.template)）。

### [5] 出来上がったものを評価する

マージされた機能を実際に使ってみて、狙い通り動いているか、想定外の挙動はないか、次に欲しい改善は何かを評価する。
この評価から生まれた気づきは、また [0] の一行イシューとして書き留められ、ループが継続する。

## なぜこの外側のループが重要か

note記事が扱う4段階フローは「イシューをどうコードにするか」という**内側**の工程を保証する仕組みである。
しかし実際にプロダクトが前進するかどうかは、外側の「何をイシューにするか」「出来上がったものが本当に
良かったか」を回すループの質にかかっている。

- 抽象的な思いつきを、いきなり大きな仕様として書き下ろさない（[0]→[1] で必ず一度小さく具体化してから
  内側の4段階フローに渡す）
- 出来上がったものを評価せずに次の実装に進まない（[4]→[5] を飛ばすと、量産はされるが的外れなPRが
  積み上がるリスクがある）
- 評価は必ず次のイシューという形で外部化する（揮発する感想で終わらせない。[5]→[0] の接続を切らない）

## なぜ一行イシューから始められるのか

[0] で「一行イシューで足りる」と述べたが、これは一見するとAIがその一行だけを読んでゼロから
要件を膨らませているように見える。実態は違う。

SoloXPで一行イシューが成立するのは、AIがその一行だけを読んで仕事をするからではない。GitHubには
過去のIssue・PR・実装コード・テスト・判断履歴・CLAUDE.md・スキル定義が蓄積されており、それらを
探索可能なコンテキストとして利用することを前提としている。たとえば「E2Eの既存REDの所有権なんとかする」
という一行だけでも、AI側からすればリポジトリに残る関連Issue・PR・現在の実装・テスト・CLAUDE.mdを
横断的に探索すれば、

```
ワンラインの意図 + 蓄積されたコンテキスト → かなり具体的なイシュー
```

まで復元できる。したがってGitHubは単なる「タスク管理＋ソース管理」ではなく、**AIの外部記憶装置**
としても機能している。Issue/PRは単なる進捗管理の記録ではなく、次の開発サイクルでAIが意図を
補完するための外部記憶でもある。これが「なぜそんな雑な一行から始めて大丈夫なのか」への回答になる。

### ループが回るほど強くなる

この外部記憶は、ループを1周するごとに厚みを増す。

```
Issueを書く → PRができる → 判断履歴が残る →
次のIssueを書く → AIが過去を参照して補完する → またIssue/PRが増える
```

つまりこの6ステップのループは、開発成果物だけでなく、**次にAIが仕事をするためのコンテキストそのもの
を毎回生産している。** ループを重ねるほど一行イシューの復元精度が上がっていく、というのがSoloXPの
根っこにある前提条件である。

### 仕様書を捨てているわけではない

以上を踏まえると、SoloXPの根幹は次のように言い換えられる。

> 「大きな仕様書を先に作る」のではなく、「小さなIssue/PRを回し、その履歴自体を次の仕様理解の
> コンテキストにする」

仕様書を書く行為自体を放棄しているわけではない。仕様を一箇所の巨大文書として固定するのではなく、
コードとIssue/PRの履歴の中に漸進的に育てている、というのが実態に近い。

## まとめ

```
抽象的な思いつき
   │ 一行イシュー
   ▼
AIとの相談で具体化
   │ 起票
   ▼
note記事の4段階フローでコード化（Architect→Tester/Implementer/Auditor/Documenter→PR）
   │ PR
   ▼
人間による確認
   │ 使ってみる
   ▼
評価
   │ 気づき
   └──▶ 新しい一行イシューとして [0] へ戻る
```

「抽象的なものを相談して具体化する」→「具体化したものを細分化する」→「少しずつ確認してマージする」→
「使ってみてまたイシューを立てる」というサイクルこそが、ソロXPの実態である。
