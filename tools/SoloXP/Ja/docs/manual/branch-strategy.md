# ブランチ・PRマージ戦略についてのメモ

SoloXPが前提にしているブランチ運用・PRマージのパターンについてのノウハウ集。
`WORKFLOW.md` が「何が起きるか」の手順書だとすると、こちらは「なぜそうなっているか」
「デフォルトと違うやり方をしたい場合に何を変えればよいか」を補足するメモ。

> **Git・GitHubに不慣れな場合**: このページは `rebase`・`merge`・`--base` 等のGit用語を
> 前提にしている。「そもそもなぜSoloXPはブランチをこう使うのか」を比喩で先に掴みたい場合は
> [SoloXPはなぜブランチをこう使うのか（超入門）](./branch-concept.md) を先に読むこと。

> **重要**: この文書が説明する範囲は SoloXP のワークフローが強制している仕組みではなく、
> `CLAUDE.md.template` の記述と `xp_Director` の実装が前提にしている**1つの規約（コンベンション）**
> にすぎない。GitHubへの他のPRマージ戦略（trunk-based以外の運用等）も原理的には可能だが、
> その場合は後述の通りカスタムが必要になる。
>
> また、実際のリベース・コンフリクト解消はほとんどの場合コーディングエージェント（Claude Code /
> Codex 等）が自動でやってくれる。以下は「エージェント任せにするにしても、裏で何が起きているか
> を知っておくと詰まったときに役立つ」という位置づけの知識。

## 1. Issueとブランチの対応関係

作業を始める前に、以下の3つが（多くはSoloXP側の規約で自動的に）決まる：

| 決めること | デフォルトの規約 | 変更するには |
|---|---|---|
| 作業対象イシュー | ユーザーが選ぶ（`/xp_Director <issue番号>` の引数、または引数なしで自動選択） | — |
| ブランチ名 | 親Story/Bug: `feature/issue-{番号}` 固定。サブTask: Claude Code等が自動生成したブランチ名をそのまま使う | ブランチ命名規則を変えたい場合は `CLAUDE.md` の「ブランチ命名規則」節を書き換える |
| ベースブランチ | プロジェクトのデフォルトブランチ（`CLAUDE.md.template` の `<デフォルトブランチ名、例: main>`。多くの場合 `main`） | 2. を参照 |

## 2. 基本形: 親ブランチにサブTaskのPRを積み上げ、AllGREEN後にmainへ

`[Story]`・`[Bug]` イシューの場合、`xp_Architect` がサブイシューへ分解した後、
`feature/issue-{親番号}` という**親ブランチ**が1本作られる。以降の流れ：

```
main
 └── feature/issue-{親番号}          ← 親ブランチ（Architect完了時に作成）
      ├─ サブTask #1 の作業ブランチ → PR（--base feature/issue-{親番号}）→ マージ
      ├─ サブTask #2 の作業ブランチ → PR（--base feature/issue-{親番号}）→ マージ
      └─ サブTask #3 の作業ブランチ → PR（--base feature/issue-{親番号}）→ マージ
           ↓（全サブTaskが [Auditor GREEN] かつ対応PRがマージ済み = AllGREEN）
      feature/issue-{親番号} → main へのPR発行・マージ
```

- 各サブTaskのPRは親ブランチへマージされる（`main` へは直接マージされない）
- 全サブTaskがAllGREENになったところで、初めて `feature/issue-{親番号}` → `main` のPRが発行される
- `[Task]` タグ単体のイシュー（Architectがバイパスされるケース）には親ブランチが存在せず、
  最初から `main` を直接ベースにしたPRになる（[使い方チュートリアル](./tutorial.md) の実例を参照）

この「サブタスクの変更を中間ブランチに積み上げてから最後にまとめてデフォルトブランチへ」という
形が、SoloXPのデフォルトが前提にしているPRマージ戦略。

## 3. `main` 以外へマージしたい場合はカスタムが必須

`dev` ブランチ等、`main` 以外を中間の統合ブランチとして使いたい場合（例:
`feature/issue-{番号}` → `dev` → 定期的に `dev` → `main`）は、SoloXPのデフォルト実装では
サポートされていない。カスタムする箇所は主に2つ：

1. `CLAUDE.md.template` の「AllGREEN 後」節にある `<デフォルトブランチ名、例: main>` を
   実際に使いたいブランチ名に変更する
2. `xp_Director` がAllGREEN時に発行するPRコマンド（`gh pr create --base main --head
   feature/issue-{親番号}`）・ルートタスクPRのコマンド（`--base main`）を、使いたいベース
   ブランチに置き換える（スキル定義の書き換えが必要）

`CLAUDE.md` 側だけ書き換えても `xp_Director` のスキル定義側が `main` 決め打ちのままだと
片手落ちになるので、両方セットで変更すること。

## 4. ソロ運用でもマージコンフリクトはそこそこ起きる

「1人での開発だからコンフリクトとは無縁」ではない。SoloXPの運用は次のような理由で
コンフリクトが発生しやすい構造になっている：

- **優先度の高いタスクへの割り込み**: あるサブTaskを処理中に緊急のバグ報告が来て、
  先にそちらを `main` に直接マージ → 後で元のサブTaskに戻ると、サブTaskの作業ブランチや
  親ブランチが古くなっている
- **サブTaskの並行処理**: 同じ親ブランチに対して複数のサブTaskが順番にマージされていくため、
  後から着手するサブTaskは常に「他のサブTaskの変更を取り込んだ最新の親ブランチ」にリベース
  してから作業する必要がある（`WORKFLOW.md` のサブTask処理フローの `git rebase
  origin/feature/issue-{親番号}` はこのためのステップ）
- **長期化したStory**: 親ブランチが作成されてからAllGREENになるまでの期間が長いほど、
  その間に `main` 側が進んでいる可能性が高くなる（5. 参照）

いずれもコーディングエージェントが `git rebase` / コンフリクト解消を代行してくれることが
多いが、「なぜリベースが必要になっているか」を理解しておくと、エージェントの提案が
おかしいときに気づきやすい。

## 5. 親ブランチ → main のPR発行時、mainの方が進んでいることが多い

親ブランチ (`feature/issue-{番号}`) は Story/Bug の着手時に一度だけ `main` から切られる。
そこからAllGREENになって `main` へのPRを出すまでの間（サブTaskを順番に処理していく期間）、
`main` 側は他の作業（別Issueのマージ等）でどんどん進んでいく。そのため、いざ親ブランチを
`main` へPRするタイミングでは、**親ブランチの派生元が古くなっている**ことがほとんど。

`xp_Director` のAllGREENフロー自体は `gh pr create --base main --head
feature/issue-{親番号}` を実行するだけで、事前に `main` の最新化・リベースを自動で行う
ステップは持っていない。つまりこの「親ブランチを最新の `main` に追従させる」作業は、
スキル定義に明示されたステップではなく、コーディングエージェントが一般的なPR運用の一環
として（コンフリクト検知時に）判断して行うことが多い、という位置づけになる。

具体的には以下のような対応が必要になる：

```bash
git fetch origin main
git merge origin/main   # または git rebase origin/main
# コンフリクトがあれば解消してコミット・push
```

マージ・リベースどちらを選ぶかはプロジェクトの方針次第（親ブランチにサブTaskのマージ
コミットが複数積まれているため、リベースだと履歴の書き換えが大きくなりやすい。多くの
場合は `merge` の方が親ブランチの運用とは相性がよい）。

## 6. Claude Code Web とローカル/PC環境でのブランチ作成の違い

Claude Code Web版では、**セッション開始時点でブランチが自動生成される**（`main` を元にした
ブランチ）。これがローカル/PC環境の挙動と異なる点：

| 環境 | ブランチの決まり方 |
|---|---|
| ローカル/PC | 明示的に `git checkout -b feature/issue-{番号}` する（どのブランチから切るかを都度自分で選べる） |
| Claude Code Web | セッション起動時に `main` ベースで自動生成されたブランチが既に存在する。Story/Bugの親ブランチを作る場面では、`xp_Director` はこの自動生成ブランチを**そのまま `feature/issue-{番号}` としてリネームして使う**（「既に存在する場合はスキップ」＝ローカルのように改めて `checkout -b` はしない） |

サブTask処理の場合も同様に、Claude Code Web のセッションブランチ（`main` ベースで
自動生成されたもの）に対して `git rebase origin/feature/issue-{親番号}` を実行し、
親ブランチに追従させてから作業する。つまり Claude Code Web では「まず `main` ベースの
ブランチが用意され、そこから親ブランチに乗り換える（リネームまたはリベース）」という
一手順が挟まる点に留意する。ローカル/PC環境でこの手順を真似る場合は、`main` ではなく
最初から `feature/issue-{親番号}` を fetch してそこからブランチを切れば同じ状態になる。

Claude Code Web特有の他の注意点（`gh auth status` の誤検出、プレビュー環境URLの導出等）は
[Claude Code Web 環境での運用ノウハウ](./claude-code-web.md) を参照。

## まとめ

- SoloXPのデフォルトは「サブTaskのPRを親ブランチに積み上げ、AllGREEN後に `main` へPR」という
  1本のトランクベース運用を前提にした**規約**であり、ワークフローエンジンが強制する制約では
  ない
- `main` 以外へのマージパターンを使うにはCLAUDE.md側・xp_Director側の両方を書き換えるカスタム
  が必要
- ソロ運用でも「優先度割り込み」「長期化したStory」「サブTaskの直列処理」の3つの理由で
  マージコンフリクトは普通に起きる。特に親ブランチ→mainのPRは、mainが先に進んでいることが
  多いため、事前のmerge/rebaseが実質的に必要になる場面が多い
- Claude Code Webとローカル/PC環境ではブランチの初期生成のされ方が異なる。Web版は
  「`main`ベースで自動生成→親ブランチへ乗り換え」という一手順を挟む
- これらのコンフリクト対応は普段はコーディングエージェントに任せて問題ないが、
  何が起きているかを理解しておくと、想定外の挙動に気づきやすくなる
